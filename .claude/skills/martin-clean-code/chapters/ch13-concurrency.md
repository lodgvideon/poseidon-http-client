# Chapter 13: Concurrency

*by Brett L. Schuchert*

> *"Objects are abstractions of processing. Threads are abstractions of schedule."* — James O. Coplien

## Core Idea
**Concurrency is a decoupling strategy** — it decouples *what* gets done from *when* it gets done. That decoupling buys throughput and structure, but it changes the design fundamentally, and it must be isolated behind SRP or the resulting bugs will be subtle, rare, and unrepeatable.

## Why Concurrency

In single-threaded applications *what* and *when* are so strongly coupled that the entire application state can often be read off a stack backtrace — set breakpoints, and you know where you are. Decoupling them makes the application *"look like many little collaborating computers rather than one big main loop."*

Three concrete motivations beyond structure:
- **Throughput under I/O wait** — a single-threaded aggregator hitting web sites in sequence spends most of its time waiting at sockets. As sites are added, the daily run eventually exceeds 24 hours.
- **Response time under load** — one second per user is fine for a few users. *"No user wants to get in line behind 150 others!"*
- **Parallel data sets** — when a complete answer requires processing everything, each data set can go to a different computer.

## Myths and Misconceptions

| Myth | Reality |
|---|---|
| Concurrency always improves performance | Only when there is **a lot of wait time that can be shared** between threads or processors. *"Neither situation is trivial."* |
| Design does not change when writing concurrent programs | The design of a concurrent algorithm *"can be remarkably different"* — decoupling what from when has a huge effect on structure |
| Understanding concurrency doesn't matter inside a Web/EJB container | *"You'd better know just what your container is doing"* and how to guard against concurrent update and deadlock |

**Balanced statements:**
- Concurrency incurs overhead — in performance **and** in extra code.
- Correct concurrency is complex, **even for simple problems**.
- **Concurrency bugs aren't usually repeatable**, so they get written off as one-offs instead of the true defects they are.
- Concurrency often requires a fundamental change in design strategy.

## The Challenge, Quantified

```java
public class X {
    private int lastIdUsed;
    public int getNextId() { return ++lastIdUsed; }
}
```

Set `lastIdUsed` to 42, share the instance between two threads, both call `getNextId()`. Three possible outcomes: (43, 44) → 44; (44, 43) → 44; and **(43, 43) → 43** — the two threads step on each other.

**The path count** — working from the generated byte-code alone:

| Field type | Possible execution paths for two threads through that one line |
|---|---|
| `int` | **12,870** |
| `long` | **2,704,156** |

*"Of course most of those paths generate valid results. The problem is that some of them don't."*

## Concurrency Defense Principles

- **Single Responsibility Principle** — *"Concurrency design is complex enough to be a reason to change in its own right and therefore deserves to be separated from the rest of the code."*
  - Concurrency code has its own life cycle of development, change, and tuning.
  - Its challenges are different from — and often harder than — non-concurrency code.
  - The number of ways miswritten concurrency code can fail is challenging enough without the burden of surrounding application code.
  - > **Recommendation: Keep your concurrency-related code separate from other code.**

- **Corollary: Limit the Scope of Data** — the more places shared data can be updated, the more likely you **forget to protect one** (breaking all code that touches it), the more **duplicated guarding effort** (a DRY violation), and the harder to find the source of failures.
  - > **Recommendation: Take data encapsulation to heart; severely limit the access of any data that may be shared.**

- **Corollary: Use Copies of Data** — avoid sharing in the first place: copy objects and treat them read-only, or collect results in per-thread copies and merge in a single thread.
  - On the cost objection: worth experimenting, but *"if using copies of objects allows the code to avoid synchronizing, the savings in avoiding the intrinsic lock will likely make up for the additional creation and garbage collection overhead."*

- **Corollary: Threads Should Be as Independent as Possible** — each thread in its own world, all required data from an unshared source, stored in local variables. `HttpServlet` subclasses get everything through `doGet`/`doPost` parameters; **so long as the servlet uses only local variables there is no chance of synchronization problems** — though most applications eventually hit shared resources like database connections.
  - > **Recommendation: Attempt to partition data into independent subsets that can be operated on by independent threads, possibly in different processors.**

## Reference Table: Concurrency Vocabulary

| Term | Definition |
|---|---|
| **Bound Resources** | Resources of fixed size or number used concurrently — database connections, fixed-size read/write buffers |
| **Mutual Exclusion** | Only one thread can access shared data or a shared resource at a time |
| **Starvation** | A thread or group is prohibited from proceeding for an excessively long time or forever — e.g. always letting fast threads through first starves long-running ones |
| **Deadlock** | Two or more threads waiting for each other to finish; each holds a resource the other requires |
| **Livelock** | Threads in lockstep, each trying to work but finding another "in the way" — due to resonance, they keep trying and never progress |

## Reference Table: The Three Fundamental Execution Models

| Model | Shape | The hard part |
|---|---|---|
| **Producer-Consumer** | Producers put work in a bounded queue; consumers take it out. Both signal each other — producers signal "no longer empty," consumers signal "no longer full" | The queue is a **bound resource**: producers wait for space, consumers wait for work |
| **Readers-Writers** | A shared resource mostly read, occasionally written | Balancing throughput against staleness. Making writers wait for zero readers **starves writers** under continuous reads; prioritizing writers **destroys throughput** |
| **Dining Philosophers** | N philosophers, N forks, each needs two forks to eat | Threads competing for resources. Without careful design: deadlock, livelock, throughput and efficiency degradation |

*"Most concurrent problems you will likely encounter will be some variation of these three problems."*
> **Recommendation: Learn these basic algorithms and understand their solutions.**

## Know Your Library (Java 5+)
- Use the provided **thread-safe collections** — `java.util.concurrent`. `ConcurrentHashMap` *"performs better than `HashMap` in nearly all situations,"* allows simultaneous concurrent reads and writes, and supports composite operations that are otherwise not thread safe. **If Java 5 is the deployment environment, start with `ConcurrentHashMap`.**
- Use the **executor framework** for unrelated tasks.
- Use **nonblocking solutions** when possible.
- Be aware that **several library classes are not thread safe.**

| Class | What it is |
|---|---|
| `ReentrantLock` | A lock that can be acquired in one method and released in another |
| `Semaphore` | The classic semaphore — a lock with a count |
| `CountDownLatch` | Waits for N events before releasing all waiting threads — gives all threads a fair chance to start at about the same time |

> **Recommendation: Become familiar with `java.util.concurrent`, `java.util.concurrent.atomic`, `java.util.concurrent.locks`.**

## Anti-patterns and Guards

- **Dependencies Between Synchronized Methods** — `synchronized` protects an *individual method*. More than one synchronized method on the same shared class means the system **may be written incorrectly**.
  - > **Recommendation: Avoid using more than one method on a shared object.**
  - When you must, there are exactly three correct approaches:
    1. **Client-Based Locking** — the client locks the server before the first call and holds the lock past the last call.
    2. **Server-Based Locking** — the server exposes one method that locks, calls everything, and unlocks.
    3. **Adapted Server** — an intermediary performs the locking (server-based locking when the original server can't be changed).

- **Oversized synchronized sections** — locks are expensive: they create delays and add overhead, so don't litter code with them. But naively enlarging critical sections to reduce their count *"increases contention and degrades performance."*
  - > **Recommendation: Keep your synchronized sections as small as possible.**

- **Shutdown code** — *"Writing correct shut-down code is hard."* Two failure shapes named:
  - A parent waits for all children before releasing resources — **one deadlocked child means the system never shuts down**.
  - A producer/consumer pair: the producer receives the shutdown signal and exits quickly; **the consumer is blocked waiting for a message that will never come**, so it can't receive its own shutdown signal, and the parent never finishes.
  - > **Recommendation: Think about shut-down early and get it working early. It's going to take longer than you expect.**

## Testing Threaded Code

> **Recommendation: Write tests that have the potential to expose problems and then run them frequently, with different programmatic configurations and system configurations and load. If tests ever fail, track down the failure. Don't ignore a failure just because the tests pass on a subsequent run.**

Seven fine-grained rules:

1. **Treat spurious failures as candidate threading issues** — bugs may appear once in a thousand or a million executions, which tempts developers to blame cosmic rays or hardware. *"It is best to assume that one-offs do not exist. The longer these 'one-offs' are ignored, the more code is built on top of a potentially faulty approach."*
2. **Get your nonthreaded code working first** — put logic in POJOs that are not thread-aware and can be tested outside the threaded environment. *"Do not try to chase down nonthreading bugs and threading bugs at the same time."*
3. **Make your threaded code pluggable** — runnable with one thread / several / varying; against real collaborators or test doubles; with doubles that run fast, slow, or variably; for a configurable number of iterations.
4. **Make your threaded code tunable** — getting the right thread count takes trial and error. Time the system under different configurations early; allow tuning at runtime; consider self-tuning on throughput and utilization.
5. **Run with more threads than processors** — *"The more frequently your tasks swap, the more likely you'll encounter code that is missing a critical section or causes deadlock."*
6. **Run on different platforms** — a course developed under OS X was taught on Windows XP in a VM; tests written to *demonstrate failure* **failed far less often on XP**, though the code was known to be incorrect. Different operating systems have different threading policies. *(Note: the JVM does not guarantee preemptive threading — modern OSes provide it "for free," but it is not guaranteed.)*
7. **Instrument your code to force failures.**

## Worked Example: Jiggling

Flaws hide because only a very few of thousands of possible pathways actually fail, so the probability of taking a failing path is startlingly low.

**Hand-coded:**

```java
public synchronized String nextUrlOrNull() {
    if (hasNext()) {
        String url = urlGenerator.next();
        Thread.yield();          // inserted for testing.
        updateHasNext();
        return url;
    }
    return null;
}
```

*"If the code does break, it was not because you added a call to `yield()`. Rather, your code was broken and this simply made the failure evident."*

Problems with hand-coding: you must manually find the places; you can't know which call to use or where; leaving it in production needlessly slows things down; *"it's a shotgun approach… Indeed, the odds aren't with you."*

**Automated:**

```java
public class ThreadJigglePoint {
    public static void jiggle() { }
}

public synchronized String nextUrlOrNull() {
    if (hasNext()) {
        ThreadJigglePoint.jiggle();
        String url = urlGenerator.next();
        ThreadJigglePoint.jiggle();
        updateHasNext();
        ThreadJigglePoint.jiggle();
        return url;
    }
    return null;
}
```

Two implementations: one that does nothing (production), one that randomly chooses among sleeping, yielding, or falling through (test). Run the tests a thousand times with random jiggling. *"If the tests pass, at least you can say you've done due diligence."* IBM's **ConTest** does the same thing with far more sophistication.

> **Recommendation: Use jiggling strategies to ferret out errors.**

## Key Takeaways
1. Concurrency decouples *what* from *when* — adopt it for structure or for wait-time throughput, not reflexively for speed.
2. A single `++` on a shared field has 12,870 execution paths; correctness intuition does not survive threading.
3. Apply SRP: separate thread-aware code from thread-ignorant POJOs, and keep the thread-aware part small and focused.
4. Limit shared data ruthlessly — encapsulate it, copy it, or partition it so threads need share nothing.
5. Learn Producer-Consumer, Readers-Writers, and Dining Philosophers; most real problems are variations of these.
6. Avoid calling more than one method on a shared object; when unavoidable, use client-based, server-based, or adapted-server locking.
7. Keep synchronized sections minimal — enlarging them to reduce their count increases contention.
8. Plan graceful shutdown early; it takes longer than expected and deadlocks there are common.
9. Never dismiss a spurious failure. Run threaded tests on all target platforms, with more threads than processors, and jiggle to force rare orderings.
