# Chapter 7: SRP — The Single Responsibility Principle

*Part III: Design Principles*

## Core Idea
**"A module should be responsible to one, and only one, actor."** SRP is *not* "a module should do one thing" — that is a different, lower-level principle. SRP is about **who** can demand a change.

## Framework: The Three Statements of SRP

The principle's evolution, each version fixing a flaw in the last:

| Version | Statement | Problem it fixes / has |
|---|---|---|
| Historical | *"A module should have one, and only one, **reason to change**."* | "Reason" is vague — reasons are *people* |
| Rephrased | *"A module should be responsible to one, and only one, **user or stakeholder**."* | Multiple people usually want the same change |
| **Final** | **"A module should be responsible to one, and only one, *actor*."** | An **actor** = the group of one or more people who require that change |

**On the name**: *"Of all the SOLID principles, the SRP might be the least well understood. That's likely because it has a particularly inappropriate name."* Programmers hear it and assume every module should do just one thing.

> *"Make no mistake, there is a principle like that. **A function should do one, and only one, thing.** We use that principle when we are refactoring large functions into smaller functions; we use it at the lowest levels. **But it is not one of the SOLID principles — it is not the SRP.**"*

**What is a "module"?** *"The simplest definition is just a source file."* When languages don't use source files, a module is *"just a cohesive set of functions and data structures."* And that word matters: **"Cohesion is the force that binds together the code responsible to a single actor."**

## Worked Example: The `Employee` Class

`Employee` has three methods — and three masters:

| Method | Specified by | Reports to |
|---|---|---|
| `calculatePay()` | Accounting department | **CFO** |
| `reportHours()` | Human resources department | **COO** |
| `save()` | Database administrators | **CTO** |

*"By putting the source code for these three methods into a single `Employee` class, the developers have coupled each of these actors to the others."*

### Symptom 1: Accidental Duplication — the million-dollar bug

The failure chain, told in order:

1. `calculatePay()` and `reportHours()` share an algorithm for **non-overtime hours**.
2. The developers, *"who are careful not to duplicate code,"* extract it into `regularHours()`. **This is the trap: correct DRY practice, wrong grouping.**
3. The **CFO's team** decides the non-overtime calculation needs a tweak. The **COO's team in HR does not want that tweak** — they use non-overtime hours for a different purpose.
4. A developer makes the change, sees `regularHours()` called by `calculatePay()`, and **does not notice it is also called by `reportHours()`**.
5. The change is carefully tested. The CFO's team validates it. It ships.
6. *"Of course, the COO's team doesn't know that this is happening. The HR personnel continue to use the reports generated by the `reportHours()` function — but now they contain incorrect numbers."*
7. *"Eventually the problem is discovered, and **the COO is livid because the bad data has cost his budget millions of dollars**."*

> *"These problems occur because we put code that different actors depend on into close proximity. **The SRP says to separate the code that different actors depend on.**"*

### Symptom 2: Merges

- The **CTO's DBAs** decide the `Employee` table needs a schema change.
- The **COO's HR clerks** need a change to the hours report format.
- Two developers, *"possibly from two different teams,"* check out `Employee` and collide. **Result: a merge.**

*"Merges are risky affairs. Our tools are pretty good nowadays, but no tool can deal with every merge case. In the end, there is always risk."* This merge puts the CTO and COO at risk — *"It's not inconceivable that the CFO could be affected as well."*

*"There are many other symptoms that we could investigate, but they all involve **multiple people changing the same source file for different reasons**."*

## Reference Table: Three Solutions

All of them **move the functions into different classes**.

| Solution | Structure | Trade-off |
|---|---|---|
| **Separate data from functions** (Fig 7.3) | `EmployeeData` is a plain data structure with no methods; `PayCalculator`, `HourReporter`, `EmployeeSaver` each hold only their own code and **are not allowed to know about each other** | *"Any accidental duplication is avoided"* — but developers now have **three classes to instantiate and track** |
| **Facade** (Fig 7.4) | `EmployeeFacade` contains very little code — it instantiates and delegates to the three classes | Restores a single entry point |
| **Facade over the important method** (Fig 7.5) | Keep the most important business rule in the original `Employee` class; use it as a Facade for the lesser functions | For developers who *"prefer to keep the most important business rules closer to the data"* |

**The "one function per class" objection, answered**: *"This is hardly the case. The number of functions required to calculate pay, generate a report, or save the data is likely to be large in each case. Each of those classes would have many private methods in them."* Each such class **is a scope** — *"Outside of that scope, no one knows that the private members of the family exist."*

## Mental Models
- **Ask "whose desk does the change request come from?" before grouping code.** Two methods belong together only if the same actor commissions changes to both.
- **DRY is not unconditional.** Extracting a shared algorithm across actor boundaries manufactures the accidental-duplication bug. Duplication *between different actors' code is often correct*.
- **Read merge conflicts as SRP violations.** Repeated collisions in one file mean multiple actors are editing it for unrelated reasons.

## Anti-patterns
- **"Every module should do one thing"** — the misreading the name invites.
- **Deduplicating across actor boundaries** — the exact move that caused the millions-of-dollars bug.
- **A class whose methods answer to different org-chart branches** — CFO, COO, and CTO in one file.

## Key Takeaways
1. SRP is about actors, not about doing one thing. Group code by who asks for changes.
2. Cohesion = the force binding code responsible to a *single* actor.
3. Accidental duplication is the signature symptom: an innocent shared helper silently couples two departments.
4. Repeated merges in one file are the second symptom — same root cause.
5. Separate the data from the functions, then optionally re-front with a Facade.
6. Small classes are not one-function classes; each is a scope full of private methods.
