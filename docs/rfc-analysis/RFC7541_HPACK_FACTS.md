| `6-46` | MUST | (§5.2) Padding bits that are not the most significant bits of the EOS code (i.e. not all ones) are a decoding error. <br>_(decoder [CLIENT])_ | A padding not corresponding to the most significant bits of the code for the EOS symbol MUST be treated as a decoding error. | hpack/huffman_fsm.go: only mark states reachable via all-ones partial input as accepting; a 0-bit in padding must fail decode. |
| `6-47` | MUST | (§5.2) A Huffman-encoded string that actually contains the complete EOS symbol is a decoding error. <br>_(decoder [CLIENT])_ | A Huffman-encoded string literal containing the EOS symbol MUST be treated as a decoding error. | hpack/huffman.go: the 30-bit EOS code must never be emitted as a decoded symbol — FSM must route full-EOS to an error state, not to symbol 256. |

### 7541 section 7 - Security Considerations

| ID | Level | Requirement (scope) | RFC 7541 verbatim | Impl check / status |
|----|-------|---------------------|-------------------|---------------------|
| `7-1` | informative | HPACK's first named security concern is use of compression as a length-based oracle for verifying guesses about secrets sharing a compression context. <br>_(all [CLIENT])_ | Use of compression as a length-based oracle for verifying guesses about secrets that are compressed into a shared compression context. | encoder: verify the Encoder offers a way to keep secret-bearing fields out of the shared dynamic table (Sensitive/never-indexed path). |
| `7-2` | informative | HPACK's second named security concern is denial of service by exhausting a decoder's processing or memory capacity. <br>_(decoder [CLIENT])_ | Denial of service resulting from exhausting processing or memory capacity at a decoder. | decoder: every decode path (integer primitive, string primitive, dynamic table insert) must be bounded; this motivates facts 7-31..7-33. |
| `7-3` | informative | An attacker who can both define encoded header fields and observe their encoded length can adaptively confirm guesses about dynamic table state. <br>_(encoder [CLIENT])_ | they can adaptively modify requests in order to confirm guesses about the dynamic table state. | encoder + dynamic table: threat model behind never-indexed support — sensitive request headers (client encodes requests) must be able to bypass dynamic-table indexing. |
| `7-4` | informative | TLS does not hide encoded lengths, so length-oracle probing works even over TLS. <br>_(all [CLIENT])_ | while TLS provides confidentiality protection for content, it only provides a limited amount of protection for the length of that content. | encoder: do not treat TLS transport as a reason to skip never-indexed handling for sensitive fields. |
| `7-5` | informative | Padding schemes give only limited protection against a length-observing attacker and work against compression. <br>_(all [not-client])_ | Padding schemes only provide limited protection against an attacker with these capabilities | no hpack/ action — HPACK defines no padding; nothing to implement in encoder or decoder. |
| `7-6` | informative | HPACK mitigates CRIME-style attacks by requiring a guess to match an entire header field value, not individual characters. <br>_(all [CLIENT])_ | forcing a guess to match an entire header field value rather than individual characters. | encoder: dynamic/static table lookup must match on exact full name+value only — never prefix or partial matching, which would reintroduce character-at-a-time oracles. |
| `7-7` | informative | Header field values with low entropy remain vulnerable to brute-force guessing through the compression oracle. <br>_(encoder [CLIENT])_ | values with low entropy remain vulnerable. | encoder: support marking low-entropy sensitive values (session cookies, tokens) never-indexed via the Sensitive flag. |
| `7-8` | informative | Probing attacks are possible whenever mutually distrustful entities place requests or responses on a single HTTP/2 connection sharing one HPACK context. <br>_(all [CLIENT])_ | Attacks of this nature are possible any time that two mutually distrustful entities control requests or responses that are placed onto a single HTTP/2 connection. | encoder + client pool: document that pooled conns assume a single trust domain; if multi-tenant load generation shares one conn, sensitive fields need never-indexed. |
| `7-9` | informative | Web browsers must treat requests from different web origins on the same connection as coming from mutually distrustful entities. <br>_(endpoint [not-client])_ | requests made on the same connection by different web origins [ORIGIN] are made by mutually distrustful entities. | no hpack/ action for a per-authority pooled load-gen client; becomes relevant only if cross-origin connection coalescing is ever added at the client layer. |
| `7-10` | informative | Using sufficiently high-entropy header values defeats guessing but is impractical as a general mitigation because it burdens all HTTP users. <br>_(all [not-client])_ | Users of HTTP that require confidentiality for header fields can use values with entropy sufficient to make guessing infeasible. | no hpack/ action — advice to HTTP users, not the codec. |
| `7-11` | informative | An HPACK implementation can constrain how compression is applied to limit dynamic table probing rather than constraining users. <br>_(encoder [CLIENT])_ | an implementation of HPACK can instead constrain how compression is applied in order to limit the potential for dynamic table probing. | encoder: verify an indexing-policy control point exists (per-field Sensitive flag or equivalent) so callers can constrain compression. |
| `7-12` | informative | The ideal mitigation segregates dynamic table access by the entity that constructed each header field, optionally tagging some entries public. <br>_(encoder [not-client])_ | An ideal solution segregates access to the dynamic table based on the entity that is constructing header fields. | encoder + dynamic table: entity segregation not needed for a single-entity client codec; note as design option if per-tenant isolation on shared conns is ever required. |
| `7-13` | informative | An encoder without provenance knowledge might penalize header fields seen with many different values by ceasing to compare them against dynamic table entries. <br>_(encoder [not-client])_ | a large number of attempts to guess a header field value results in the header field no longer being compared to the dynamic table entries in future messages | encoder: optional anti-probing heuristic; not required for a single-trust-domain client — record as deliberate non-goal. |
| `7-14` | informative | Merely evicting the targeted entry is an ineffective mitigation if the attacker can reliably cause the value to be reinstalled in the table. <br>_(encoder [not-client])_ | Simply removing entries corresponding to the header field from the dynamic table can be ineffectual if the attacker has a reliable way of causing values to be reinstalled. | encoder + dynamic table: if an eviction-based mitigation is ever considered, it must stop future indexing of the field, not just evict once. |
| `7-15` | informative | The stop-indexing penalty might trigger faster or with higher probability for shorter values, since short values are easier to brute-force. <br>_(encoder [not-client])_ | Marking a header field as not using the dynamic table anymore might occur for shorter values more quickly or with higher probability than for longer values. | encoder: refinement of the optional 7-13 heuristic; no action for current single-tenant encoder. |
| `7-16` | informative | Implementations can protect sensitive header fields by not compressing them and encoding their values as literals instead. <br>_(encoder [CLIENT])_ | Implementations can also choose to protect sensitive header fields by not compressing them and instead encoding their value as literals. | encoder: verify Sensitive fields are emitted as literal representations that never add to the dynamic table (Section 6.2.3 form). |
| `7-17` | informative | Refusing to index protects only if avoided on every hop, so the never-indexed literal exists to signal intermediaries the literal encoding was intentional. <br>_(encoder [CLIENT])_ | Refusing to generate an indexed representation for a header field is only effective if compression is avoided on all hops. | encoder: sensitive fields must use the never-indexed form (6.2.3), not the plain without-indexing form (6.2.2), so the protection signal survives intermediaries. |
| `7-18` | MUST NOT | An intermediary is forbidden from re-encoding a value received as a never-indexed literal with any representation that would index it. <br>_(endpoint,encoder [CLIENT])_ | An intermediary MUST NOT re-encode a value that uses the never-indexed literal representation with another representation that would index it. | decoder: decoded HeaderField must carry the never-indexed/Sensitive flag so any consumer that re-encodes (generic codec use) can honor this; verify the flag is surfaced, not dropped. |
| `7-19` | MUST | When HPACK is used to re-encode a value that arrived never-indexed, the never-indexed literal representation is mandatory. <br>_(encoder [CLIENT])_ | If HPACK is used for re-encoding, the never-indexed literal representation MUST be used. | encoder: any field flagged Sensitive must always encode as 6.2.3 never-indexed — regardless of Huffman choice or table state; add/verify a conformance test. |
| `7-20` | informative | An encoder might choose not to index low-entropy values because they are readily recovered by guessing. <br>_(encoder [CLIENT])_ | an encoder might choose not to index values with low entropy. | encoder: indexing policy — confirm callers can opt individual low-entropy values out of indexing per field, not only globally. |
| `7-21` | informative | An encoder might choose not to index highly valuable or sensitive header fields such as Cookie or Authorization. <br>_(encoder [CLIENT])_ | not to index values for header fields that are considered to be highly valuable or sensitive to recovery, such as the Cookie or Authorization header fields. | encoder: check whether Authorization/Cookie get sensitive-by-default treatment or require the caller to set the Sensitive flag; document whichever is chosen. |
| `7-22` | informative | An encoder might prefer indexing header fields whose exposure has little or no value, such as an unvarying User-Agent. <br>_(encoder [CLIENT])_ | an encoder might prefer indexing values for header fields that have little or no value if they were exposed. | encoder: compression-efficiency guidance — repeated non-sensitive request headers (User-Agent, Accept-*) should be indexable in the dynamic table. |
| `7-23` | informative | Criteria for choosing never-indexed representation will evolve as new attacks are discovered, so the policy should not be frozen. <br>_(encoder [CLIENT])_ | these criteria for deciding to use a never-indexed literal representation will evolve over time as new attacks are discovered. | encoder: keep sensitivity policy caller-configurable (per-field flag) rather than a hardcoded header-name list baked into hpack/. |
| `7-24` | informative | No known attack exists against a static Huffman encoding; a demonstrated information leak was concluded to be unexploitable. <br>_(all [CLIENT])_ | There is no currently known attack against a static Huffman encoding. | huffman: verify the codec uses only the fixed RFC 7541 Appendix B static table — never adaptive/frequency-derived codes, which would reopen oracle attacks. |
| `7-25` | informative | HPACK is designed so both peak (temporary) and state (retained) memory allocated by an endpoint are limited. <br>_(all [CLIENT])_ | HPACK is designed to limit both the peak and state amounts of memory allocated by an endpoint. | decoder + dynamic table: confirm both retained state (table max size) and transient decode allocations (string/int limits) are bounded — the two halves of facts 7-26..7-33. |
| `7-26` | informative | Compressor memory is limited by the protocol-defined maximum dynamic table size; in HTTP/2 the decoder controls it via SETTINGS_HEADER_TABLE_SIZE. <br>_(all [CLIENT])_ | this value is controlled by the decoder through the setting parameter SETTINGS_HEADER_TABLE_SIZE (see Section 6.5.2 of [HTTP2]). | encoder + dynamic table: encoder's table cap must track the peer's SETTINGS_HEADER_TABLE_SIZE (conn wiring); decoder's cap must follow our own advertised setting. |
| `7-27` | informative | The dynamic table size limit covers stored data plus a small per-entry overhead allowance. <br>_(all [CLIENT])_ | This limit takes into account both the size of the data stored in the dynamic table, plus a small allowance for overhead. | dynamic table: verify entry size accounting is len(name)+len(value)+32 per Section 4.1 in both encoder and decoder tables, and that eviction uses this size. |
| `7-28` | informative | A decoder bounds its state memory by choosing an appropriate maximum dynamic table size (its SETTINGS_HEADER_TABLE_SIZE). <br>_(decoder [CLIENT])_ | A decoder can limit the amount of state memory used by setting an appropriate value for the maximum size of the dynamic table. | decoder + dynamic table: the client's advertised SETTINGS_HEADER_TABLE_SIZE must be a hard cap on decoder table growth — a size update above it is a decode error (COMPRESSION_ERROR at conn layer). |
| `7-29` | informative | An encoder can bound its own state memory by signaling a dynamic table size lower than the decoder's allowance via a size update (Section 6.3). <br>_(encoder [CLIENT])_ | An encoder can limit the amount of state memory it uses by signaling a lower dynamic table size than the decoder allows | encoder: verify the dynamic-table-size-update (6.3) path can select any size <= peer's SETTINGS_HEADER_TABLE_SIZE and emits the update instruction before the next encoded field. |
| `7-30` | informative | Temporary memory can be bounded by processing header fields sequentially; the codec itself need not retain a complete header list. <br>_(all [CLIENT])_ | The amount of temporary memory consumed by an encoder or decoder can be limited by processing header fields sequentially. | decoder: confirm a streaming/sequential emit path exists (or that list accumulation is a deliberate conn-layer choice bounded by SETTINGS_MAX_HEADER_LIST_SIZE, not an hpack/ obligation). |
| `7-31` | informative | An implementation must ensure that large integer values, long integer encodings, and long string literals cannot create security weaknesses. <br>_(all,decoder [CLIENT])_ | An implementation of HPACK needs to ensure that large values for integers, long encoding for integers, or long string literals do not create security weaknesses. | integer + string primitives: plain-language mandatory ('needs to') — treat as MUST for audit; covers 5.1 overflow, redundant continuation-byte padding, and 5.2 length bombs. |
| `7-32` | informative | An implementation must set a limit both on the integer values it accepts and on the encoded length of integers (Section 5.1). <br>_(decoder [CLIENT])_ | An implementation has to set a limit for the values it accepts for integers, as well as for the encoded length (see Section 5.1). | integer primitive (5.1): verify decode caps the value (fits target uint without wraparound) AND caps continuation-byte count, returning an error — never panic or silent overflow; fuzz both. |
| `7-33` | informative | An implementation must likewise set a limit on the string literal lengths it accepts (Section 5.2). <br>_(decoder [CLIENT])_ | it has to set a limit to the length it accepts for string literals (see Section 5.2). | string primitive (5.2) + huffman: enforce a max string length BEFORE allocating, and bound Huffman-decoded output (expansion up to 8/5 of wire length) — plain-language mandatory, treat as MUST. |
