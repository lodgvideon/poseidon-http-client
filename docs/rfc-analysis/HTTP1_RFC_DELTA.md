# RFC 2616 -> RFC 9110/9112 Delta -- where a client built to the obsolete spec diverges from the current HTTP/1.1 slice

_Where a client BUILT TO RFC 2616 diverges from the current HTTP/1.1 slice (RFC 9110 semantics + RFC 9112 message syntax). Both quotes verbatim from the respective source; each delta re-verified by two independent Opus passes (default-refute). Rows flagged VERIFY need a manual source check._

### framing - RFC 2616 -> RFC 9110/9112 delta: message framing and body length

| ID | Change | Summary | RFC 2616 | Current (9110/9112) | Client impact | Reconcile / status |
|----|--------|---------|----------|---------------------|---------------|--------------------|
| `framing-1` | security_hardening | TE+CL together went from 'silently ignore Content-Length' to 'likely smuggling/splitting, ought to be an error'; servers that tolerate it MUST close the connection after responding. | 2616 RFC 2616 §4.4 item 3: "If a message is received with both a Transfer-Encoding header field and a Content-Length header field, the latter MUST be ignored." | RFC 9112 §6.3 item 3, §6.1: "Such a message might indicate an attempt to perform request smuggling (Section 11.2) or response splitting (Section 11.1)" | A 2616-era client silently drops CL, parses TE, and keeps the connection alive for reuse — exactly the desync sink response-splitting attacks need. Current spec: treat as error, or at minimum never reuse that connection (senders also now MUST NOT emit CL alongside TE, 9112 §6.2). | http1/conn.go response framing path + http1/conformance_te_cl_test.go: verify a response carrying both TE and CL is either rejected or parsed per TE with the connection marked non-reusable, and that the client itself can never emit CL+TE together on a request. |
| `framing-2` | security_hardening | New recipient rule: an HTTP/1.0 message carrying Transfer-Encoding has faulty framing — process then close; 2616 only had the sender-side prohibition. | 2616 RFC 2616 §3.6: "A server MUST NOT send transfer-codings to an HTTP/1.0 client." | RFC 9112 §6.1: "MUST treat the message as if the framing is faulty, even if a Content-Length is present, and close the connection after processing the message" | A 2616 client that receives 'HTTP/1.0 200 OK' + 'Transfer-Encoding: chunked' happily chunk-decodes and keeps the connection alive; an intermediary that mangled the framing may have buffered bytes that desync the next response. Current spec: treat framing as faulty and close after this message. | http1/conn.go response reader: check whether the status-line version is inspected at all; a response advertising HTTP/1.0 with any Transfer-Encoding must force close-after-message (no keep-alive reuse). Likely gap — no existing conformance test name suggests this case. |
| `framing-3` | removed | The 'identity' transfer-coding no longer exists — 2616's 'any value other than identity' escape hatch is gone; identity is now just an unknown coding. | 2616 RFC 2616 §4.4 item 2, §3.6/§3.6.2: "has any value other than "identity"" | RFC 9112 §7 (coding list: chunked, compress, deflate, gzip only): "absent" | Two failure modes: (a) sending 'Transfer-Encoding: identity' or 'TE: identity' now emits an unregistered coding (servers SHOULD 501); (b) on receive, special-casing 'identity' as 'no transformation, use CL' instead of 'TE present, chunked not final -> read-until-close' recreates the classic TE:identity desync/smuggling vector. | Grep http1/ for any 'identity' special case in Transfer-Encoding or TE handling; the decoder must treat it exactly like any other non-chunked coding (response: read-until-close, conn not reusable). http1/conformance_te_grammar_test.go is the natural home for the assertion. |
| `framing-4` | tightened | Non-chunked-final Transfer-Encoding now has exact split outcomes: response -> read-until-close; request -> server MUST 400 and close. 2616's item 2 vaguely said chunked framing 'unless terminated by closing the connection'. | 2616 RFC 2616 §4.4 item 2: "the transfer-length is defined by use of the "chunked" transfer-coding (section 3.6), unless the message is terminated by closing the connection." | RFC 9112 §6.3 item 4: "the chunked transfer coding is not the final encoding, the message body length is determined by reading the connection until it is closed" | A 2616 client reading its item 2 literally chunk-parses any TE'd message (e.g. 'Transfer-Encoding: gzip'), misinterprets compressed bytes as chunk-size lines, and produces garbage or desyncs. Current rule: chunk-decode only when 'chunked' is the FINAL listed coding; otherwise read to EOF and never reuse the connection. Also expect 400+close if the client ever sends a non-chunked-final TE request. | http1/conn.go TE evaluation: confirm it checks the LAST element of the (possibly multi-valued/multi-line) Transfer-Encoding list == 'chunked' (http1/conformance_te_grammar_test.go, conformance_te_multiline_test.go), and that non-chunked-final responses fall back to read-until-close with reuse disabled (conformance_te_unterminated_test.go). |
| `framing-5` | removed | multipart/byteranges self-delimiting framing (2616 §4.4 item 4) is gone from the body-length precedence list entirely. | 2616 RFC 2616 §4.4 item 4: "If the message uses the media type "multipart/byteranges"" | RFC 9112 §6.3 (items 1-8, no media-type rule): "absent" | A 2616 client that terminates a CL-less/TE-less Range response at the final MIME boundary stops early while the server considers the response close-delimited (or vice versa) — body-length disagreement, truncation, and poisoning on any reuse heuristic. Current rule: such a response is simply close-delimited (item 8); Content-Type must never influence framing. | Verify http1/conn.go body-length determination never inspects Content-Type (should already be true — confirm nothing special-cases multipart/byteranges, and that a Range response without CL/TE is read to EOF). |
| `framing-6` | security_hardening | Invalid Content-Length escalated from 'notify the user' to 'unrecoverable framing error': user agent MUST close the connection and discard the response. | 2616 RFC 2616 §4.4: "HTTP/1.1 user agents MUST notify the user when an invalid length is received and detected." | RFC 9112 §6.3 item 5: "then the message framing is invalid and the recipient MUST treat it as an unrecoverable error" | A 2616 client that 'notifies' but continues (best-effort parse of 'Content-Length: 4a', leading '+', negative, or empty values) is now non-conformant and smuggling-prone: any lenient parse that differs from an intermediary's parse is a desync primitive. Must hard-fail, close, and deliver nothing. | http1/conn.go Content-Length parse + http1/conformance_cl_test.go: strict 1*DIGIT only (no sign, no whitespace tricks, no hex), overflow-checked, and on failure the response errors out and the connection closes — no partial body delivery. |
| `framing-7` | added | New rule for multiple Content-Length values: recoverable only if the field parses as a list whose members are all valid and identical; otherwise unrecoverable error. | 2616 RFC 2616 §4.4 (no rule for repeated Content-Length): "absent" | RFC 9112 §6.3 item 5: "all values in the list are valid, and all values in the list are the same" | 'Content-Length: 42, 42' or duplicate CL header lines were undefined in 2616 — clients variously took the first, the last, or choked; differential parsing between client and proxy is a textbook smuggling setup. Current: accept only when every value is identical (use that value), else treat as unrecoverable and close. | http1/conn.go header-repetition handling for Content-Length: duplicate CL lines and comma-joined values must collapse only when byte-for-byte identical numeric values; anything else rejects the message. Confirm http1/conformance_cl_test.go covers both the duplicate-line and comma-list shapes. |
| `framing-8` | added | Explicit truncation rule: connection close or timeout before CL octets arrive means the message is incomplete and the recipient MUST close; 2616 only had the sender-side exact-match requirement. | 2616 RFC 2616 §4.4: "its field value MUST exactly match the number of OCTETs in the message-body" | RFC 9112 §6.3 item 6: "the recipient MUST consider the message to be incomplete and close the connection" | A 2616 client with no recipient-side rule may hand a truncated body to the application as complete on early EOF — a silent truncation attack on downloads (strip a security update's tail, cut a JSON array short). Current: surface a distinct 'incomplete' error and close. | http1/conn.go CL-body reader: short read must return an unexpected-EOF-class error (never io.EOF-as-success) and the conn must not return to any reuse path; http1/keepalive_eof_test.go is the anchor — verify it asserts the error identity, not just termination. |
| `framing-9` | added | New framing rule for CONNECT: a 2xx response means the tunnel starts right after the header section, and the client MUST ignore any CL/TE in that response. | 2616 RFC 2616 §4.4 (no CONNECT rule in the precedence list): "absent" | RFC 9112 §6.3 item 2: "A client MUST ignore any Content-Length or Transfer-Encoding header fields received in such a message." | A 2616 client that honors a Content-Length on a CONNECT 2xx swallows the first N tunnel bytes as 'response body', corrupting the tunneled protocol (typically TLS) from byte zero. Servers now also MUST NOT send TE in 2xx-to-CONNECT. | Determine whether the http1 package can issue CONNECT at all. If yes: the framing switch must special-case method==CONNECT && 2xx (zero body, hand off raw conn). If no: ensure the client layer rejects CONNECT rather than letting it fall through the normal response-framing path. No conformance test name suggests this exists — likely gap. |
| `framing-10` | security_hardening | Chunk-size parsing gained an explicit overflow mandate: recipients MUST survive arbitrarily long hex numerals without integer overflow or precision loss. | 2616 RFC 2616 §3.6.1: "The chunk-size field is a string of hex digits indicating the size of the chunk." | RFC 9112 §7.1: "recipients MUST anticipate potentially large hexadecimal numerals and prevent parsing errors due to integer conversion overflows or precision loss due to integer representation" | A 2616 client with a naive shift-accumulate hex parser wraps on 'FFFFFFFFFFFFFFFFF' into a small/negative size — desync at best, buffer bug at worst. Must cap digits/value and reject with a framing error before accumulation overflows. | http1/conn.go chunk-size parser: confirm the overflow cap and rejection path; http1/conformance_chunksize_test.go and http1/chunk_negsize_test.go exist — verify they include a >64-bit numeral and a max-int64-adjacent value, per the peer-input policy (bound by construction). |
| `framing-11` | security_hardening | New rule for bytes remaining after the final response: a client MUST NOT process, cache, or forward extra data as a separate response. | 2616 RFC 2616 §4.4 (no rule for surplus data): "absent" | RFC 9112 §6.3: "A client MUST NOT process, cache, or forward such extra data as a separate response, since such behavior would be vulnerable to cache poisoning" | A 2616 client (especially one pipelining or keeping the parser hot on an idle conn) that parses leftover bytes as the next response is the receiving end of every response-splitting attack. Current: discard the surplus or attribute it to the prior body; never mint a new response from it. | http1/conn.go keep-alive path: after a framed response completes, any unexpected buffered/readable bytes before the next request is written must poison the connection (close, no reuse), not sit as a parseable 'next response'. Check http1/injection_test.go and keepalive_eof_test.go for coverage of unsolicited bytes. |
| `framing-12` | security_hardening | Trailer handling inverted: 2616's appendix 19.4.6 decode example appended trailer fields to the headers; current spec forbids merging unless the field's definition explicitly permits it. | 2616 RFC 2616 §3.6.1 (decode algorithm in appendix 19.4.6): "An example process for decoding a Chunked-Body is presented in appendix 19.4.6." | RFC 9112 §7.1.2: "A recipient MUST NOT merge a received trailer field into the header section unless its corresponding header field definition explicitly permits" | A client built on the 2616 example merges trailers into headers, letting a peer (or upstream attacker controlling the body) inject or override authority fields after the fact — Set-Cookie, cache directives, even framing fields for downstream consumers. Current: keep trailers in a separate section or drop them. | Verify the http1 response type exposes trailers as a distinct field set and that http1/conn.go never folds trailer fields into the header map; http1/conformance_trailer_deadline_test.go covers bounding — add/confirm a no-merge assertion (also check nothing recycles the header slice across header/trailer parsing, per pooled-stream reset rules). |
| `framing-13` | relaxed | 2616's preconditions for servers using trailers (TE: trailers, or optional-metadata-only) are gone; TE 'trailers' now merely means the sender will not discard them — trailers can legitimately arrive without any opt-in. | 2616 RFC 2616 §3.6.1: "A server using chunked transfer-coding in a response MUST NOT use the trailer for any header fields" | RFC 9112 §7.4 / RFC 9110 §6.5: "The keyword "trailers" indicates that the sender will not discard trailer fields" | A 2616 client that assumes 'we never sent TE: trailers, so any trailer section is at most empty' and skips or mis-parses a populated trailer section will lose framing (the trailer terminates the chunked body). Must always parse the full trailer section of every chunked message, regardless of what TE it sent, and may then discard the fields. | http1/conn.go chunked reader: confirm the trailer section is parsed unconditionally to the terminating empty line (with size/time bounds — conformance_trailer_deadline_test.go, recvbounds_test.go) even when the client sent no TE header. |
| `framing-14` | relaxed | Chunk-extension grammar now admits BWS around ';' and '=', and gained explicit guidance to bound total extension length; unknown extensions still MUST be ignored. | 2616 RFC 2616 §3.6.1: "chunk-extension= *( ";" chunk-ext-name [ "=" chunk-ext-val ] )" | RFC 9112 §7.1.1: "chunk-ext = *( BWS ";" BWS chunk-ext-name [ BWS "=" BWS chunk-ext-val ] )" | Two-sided: a byte-strict 2616 parser rejects '1a ; ext=1' which is now grammatically valid on the wire (interop failure); and a parser with no cap on extension bytes can be fed an unbounded extension line (memory DoS) — the new text tells recipients to length-limit like any other message part. | http1/conn.go chunk-size line parser: tolerate optional whitespace before/around extensions while still rejecting garbage, and enforce a hard byte cap on the whole chunk-size line (recvbounds_test.go / peer-input policy: charge what memory retains). |
| `framing-15` | tightened | The chunked coding (and the compression codings) now define no parameters, and the presence of parameters SHOULD be treated as an error; 2616's grammar allowed ';' parameters on any transfer-extension. | 2616 RFC 2616 §3.6: "transfer-extension = token *( ";" parameter )" | RFC 9112 §7.1, §7.2: "The chunked coding does not define any parameters. Their presence SHOULD be treated as an error." | A 2616 client accepts 'Transfer-Encoding: chunked;foo=bar' as chunked; current spec says error it. Lenient acceptance here is another differential-parsing seam (an intermediary that errors vs a client that strips the parameter disagree about framing). | http1/conn.go Transfer-Encoding value parsing: 'chunked' must match as a bare token (case-insensitive), with any ';parameter' rejected — confirm http1/conformance_te_grammar_test.go includes a parameterized-chunked rejection case. |
| `framing-16` | tightened | Request-body send rules made absolute: a UA MUST send a valid CL or use chunked (never neither, never close-delimited), chunked/TE only toward servers known to be HTTP/1.1+, and SHOULD prefer CL when length is known (411 reality). | 2616 RFC 2616 §4.4: "HTTP/1.1 requests containing a message-body MUST include a valid Content-Length header field unless the server is known to be HTTP/1.1 compliant" | RFC 9112 §6.3, §6.1: "user agent that sends a request that contains a message body MUST send either a valid Content-Length header field or use the chunked transfer coding" | Mostly formalizes practice, but three checks bite: a request with a body and neither CL nor chunked is now defined as ending at the header section (server reads zero body — silent data loss, not an error); 'A client MUST NOT send a request containing Transfer-Encoding unless it knows the server will handle HTTP/1.1' (9112 §6.1); and chunked uploads to length-requiring gateways draw 411s, so known-length bodies SHOULD carry CL. | Client request-write path (http1/conn.go + client H1 transport): known-length body -> CL set exactly; unknown length -> chunked; impossible to emit a body with neither; document (or gate) the assumption that configured servers are HTTP/1.1. http1/conformance_reqframing_test.go is the anchor. |
| `framing-17` | tightened | New MUST NOT: a client may not list 'chunked' in TE (it is always acceptable); 2616 merely noted chunked is always acceptable without forbidding it in TE. | 2616 RFC 2616 §14.39: "The "chunked" transfer-coding is always acceptable." | RFC 9112 §7.4: "A client MUST NOT send the chunked transfer coding name in TE; chunked is always acceptable for HTTP/1.1 recipients." | A 2616 client emitting 'TE: chunked' (some did, defensively) now violates a MUST NOT — usually harmless but non-conformant and rejectable by strict peers. Both eras require 'TE' in the Connection header whenever TE is sent; that part is unchanged. | Confirm the client never emits a TE header at all, or if TE is exposed, that 'chunked' is filtered out and 'Connection: TE' is added alongside. Note sibling-divergence risk: HTTP/2/3 forbid TE except 'trailers' — check each stack separately (cf. the recent te-on-response http3 fix, commit 9e1b62d). |
| `framing-18` | relaxed | Request framing is now explicitly independent of method semantics; 2616 forbade including a body when the method spec didn't allow one. | 2616 RFC 2616 §4.3: "A message-body MUST NOT be included in a request if the specification of the request method (section 5.1.1) does not allow sending an entity-body" | RFC 9112 §6: "Request message framing is independent of method semantics." | A 2616 client that hard-rejects or silently strips bodies/CL on GET, HEAD, or DELETE at the framing layer is over-strict: framing-wise such requests are valid today (semantics discourage but do not forbid; interop caveats live in 9110). A load-generator client in particular must be able to emit them for testing targets. | Check the client request builder and http1 write path for any method-conditional body rejection; policy decisions (warn on GET-with-body) belong at the client layer, never in http1 framing. |
| `framing-19` | clarified | Bodyless responses (HEAD/1xx/204/304) now explicitly exclude trailers too, and Transfer-Encoding MAY legitimately appear on HEAD/304 responses as metadata (while newly forbidden on 1xx/204 and 2xx-to-CONNECT). | 2616 RFC 2616 §4.4 item 1: "is always terminated by the first empty line after the header fields, regardless of the entity-header fields present" | RFC 9112 §6.3 item 1, §6.1: "Transfer-Encoding MAY be sent in a response to a HEAD request or in a 304 (Not Modified) response" | No-op if the client already lets status/method win over headers. Bug if 'Transfer-Encoding: chunked' on a 304 or HEAD response flips the reader into chunk-decoding — it then blocks waiting for chunks that never come and misframes the next response on the reused connection. | http1/conn.go body-presence switch: HEAD requests and 1xx/204/304 statuses must short-circuit to zero body BEFORE any TE/CL inspection — http1/conformance_bodyless_test.go should include the '304 + Transfer-Encoding: chunked' and 'HEAD + chunked' combinations explicitly. |

### fields - RFC 2616 -> RFC 9110/9112 delta: field syntax, whitespace, obs-fold, octet parsing, bare CR

| ID | Change | Summary | RFC 2616 | Current (9110/9112) | Client impact | Reconcile / status |
|----|--------|---------|----------|---------------------|---------------|--------------------|
| `fields-1` | removed | Header line folding (obs-fold) is no longer a legal wire form; senders are forbidden to generate it outside message/http. | 2616 2616 §2.2: "HTTP/1.1 header field values can be folded onto multiple lines if the continuation line begins with a space or horizontal tab." | 9112 §5.2: "A sender MUST NOT generate a message that includes line folding" | A 2616 client that wraps long header values across lines now emits invalid requests; servers MUST reject them with 400. Silent hard failure against modern servers. | http1/conn.go WriteRequest + validFieldValue: confirm outgoing field values can never contain CR/LF (so no folded emission path exists). conformance_obsfold_test.go covers receive side; verify send side has a negative test too. |
| `fields-2` | tightened | Receiving obs-fold in a response: 2616's recipient MAY-replace becomes a user-agent MUST-replace with SP (no reject option for UAs). | 2616 2616 §2.2: "A recipient MAY replace any linear white space with a single SP before interpreting the field value or forwarding the message downstream." | 9112 §5.2: "MUST replace each received obs-fold with one or more SP octets prior to interpreting the field value" | A client that keeps CRLF inside the logical value, splits the fold into two headers, or rejects the response outright is nonconformant as a UA; the only allowed behavior is SP-replacement before interpretation. | http1/conn.go consumeHeaders/commitHeaderLine + logicalLine (line 1413): verify continuation lines are joined with SP (not CRLF retained, not dropped). conformance_obsfold_test.go and conformance_obsfold_cost_test.go exist -- check they assert the SP-joined value, and that framing headers (Content-Length/Transfer-Encoding) with obs-fold are still refused (see conformance_te_multiline_test.go). |
| `fields-3` | security_hardening | Bare CR (CR not followed by LF) is now explicitly prohibited in protocol elements; recipients MUST treat it as invalid or replace with SP. | 2616 2616 §2.2: "HTTP/1.1 defines the sequence CR LF as the end-of-line marker for all protocol elements except the entity-body" | 9112 §2.2: "A recipient of such a bare CR MUST consider that element to be invalid or replace each bare CR with SP before processing the element" | 2616 gave no handling rule, so 2616-era parsers variously treated lone CR as a terminator, data, or dropped it -- a desync/smuggling vector. A client must now error or SP-replace; anything else risks disagreeing with the peer about message boundaries. | http1/conn.go readLine (line 529): feed 'HTTP/1.1 200 OK\rX\r\n' and 'Name: a\rb\r\n' -- confirm bare CR inside a line is rejected or SP-replaced, never silently kept/stripped. conformance_rfc9112_test.go should pin this. |
| `fields-4` | security_hardening | CR, LF, or NUL inside a field value: recipient MUST reject the message or replace each with SP (2616 only excluded CTLs grammatically, with CRLF legal via folding). | 2616 2616 §2.2: "A CRLF is allowed in the definition of TEXT only as part of a header field continuation." | 9110 §5.5: "a recipient of CR, LF, or NUL within a field value MUST either reject the message or replace each of those characters with SP" | Header-injection / response-splitting defense. A 2616 client that passes embedded CR/LF/NUL through to the application (or re-serializes them when forwarding) is unsafe. Other CTLs are also invalid per 9110, though recipients MAY retain them in safe contexts. | http1/conn.go validFieldValue (line 241) gates the send side; verify the receive side (commitHeaderLine) also rejects or SP-replaces CR/LF/NUL in response field values. injection_test.go exists -- confirm it covers received values, not just outgoing. |
| `fields-5` | security_hardening | Whitespace between field name and colon is now explicitly forbidden; servers MUST reject such requests with 400. | 2616 2616 §4.2: "Each header field consists of a name followed by a colon (":") and the field value." | 9112 §5.1: "No whitespace is allowed between the field name and colon." | 2616's implied-LWS convention let clients emit 'Host : x' -- such requests now draw 400. On the response path, a client parser that keys headers on the raw pre-colon bytes ('Name ') fails lookups or, worse, treats a poisoned name as distinct from the real one. | http1/conn.go: validToken (line 282) should already exclude SP/HTAB from outgoing names; on receive, commitHeaderLine must treat 'Name : v' as malformed (or strip and flag), not accept 'Name ' as a field name. conformance_respfield_test.go is the likely home. |
| `fields-6` | security_hardening | A whitespace-prefixed line after the start-line is no longer a fold; recipient MUST reject the message or discard each such line. | 2616 2616 §4.2: "Header fields can be extended over multiple lines by preceding each extra line with at least one SP or HT." | 9112 §2.2: "A recipient that receives whitespace between the start-line and the first header field MUST either reject the message as invalid or consume each whitespace-preceded line" | A 2616 parser would try to fold a SP-led line following the status-line into a nonexistent previous header (undefined behavior, historically 'fold into the start-line'). Current spec closes this smuggling/splitting vector: reject or drop the line(s) entirely. | http1/conn.go ReadResponse -> consumeHeaders: send '\r\nHTTP/1.1 200 OK\r\n bogus: x\r\n...' -- the ' bogus' line must not become a header or a fold of the status line. Check the state machine distinguishes 'continuation before any header' from a legitimate obs-fold after one. |
| `fields-7` | tightened | LWS ([CRLF] 1*(SP\|HT)) is replaced by OWS/RWS = SP/HTAB only; whitespace can never contain a CRLF anymore. | 2616 2616 §2.2: "LWS = [CRLF] 1*( SP \| HT )" | 9110 §5.6.3: "OWS = *( SP / HTAB ) ; optional whitespace" | Any 2616-built tokenizer that treats CRLF+SP as ordinary whitespace inside field values, list separators, or parameters over-accepts and can be desynchronized from a strict peer -- the root enabler of fold-based smuggling. Grammar positions that used implied LWS map to OWS/RWS with no line break allowed. | Grep http1/ for any whitespace helper that accepts \r or \n as skippable whitespace (e.g. in lastTransferCoding, parseChunkSize, parseContentLength trimming). Only SP and HTAB may be treated as whitespace inside values. |
| `fields-8` | added | New BWS ('bad whitespace') class: senders MUST NOT generate it; recipients MUST parse and remove it before interpreting the element. | 2616 2616: "absent" | 9110 §5.6.3: "A sender MUST NOT generate BWS in messages. A recipient MUST parse for such bad whitespace and remove it before interpreting the protocol element." | Positions where 2616's implied LWS allowed whitespace (e.g. around '=' in chunk extensions) are now BWS: a 2616 client emitting them is nonconformant, and a client parser must tolerate-and-strip them on receipt rather than fail or preserve them. Note 9110 §5.6.6: parameters allow no whitespace at all around '='. | http1/conn.go parseChunkSize (line 1000) and transferCodingName/lastTransferCoding: check chunk-ext and coding-parameter parsing strips BWS around ';' and '=' without accepting CR/LF. conformance_chunksize_test.go / conformance_te_grammar_test.go should pin both directions. |
| `fields-9` | added | Recipients MUST parse messages as octet sequences in a US-ASCII-superset encoding, never as Unicode character streams. | 2616 2616: "absent" | 9112 §2.2: "A recipient MUST parse an HTTP message as a sequence of octets in an encoding that is a superset of US-ASCII" | 2616 defined ASCII rules but no parsing model. Clients doing string/Unicode-level processing before field delineation can mis-handle invalid multibyte sequences containing 0x0A -- a framing vulnerability. Byte-level parsing must delineate lines first; string libraries only afterwards. | http1/conn.go operates on []byte/latin-1-safe strings -- audit readLine, consumeHeaders, asciiEqualFold, asciiLowerHeaderName for any utf8/rune decoding applied before field lines are delineated (there should be none; keep it that way). |
| `fields-10` | moved | Bare-LF line-terminator tolerance moved from 2616's informative appendix 19.3 into normative text: recipient MAY accept lone LF and ignore preceding CR. | 2616 2616 §2.2 (pointing to app. 19.3): "the sequence CR LF as the end-of-line marker for all protocol elements except the entity-body (see appendix 19.3 for tolerant applications)" | 9112 §2.2: "a recipient MAY recognize a single LF as a line terminator and ignore any preceding CR" | Optional, so a strict CRLF-only client stays conformant, but modern peers commonly accept bare LF; a 2616 client is at worst interop-strict here. If the client does accept bare LF, the preceding CR must be dropped, not folded into the previous token or field value. | http1/conn.go readLine: decide and document the policy (strict CRLF vs LF-tolerant). If LF-tolerant, assert 'value\n' yields 'value' with no trailing CR ever retained; ensure this interacts safely with the bare-CR rule (fields-3). |
| `fields-11` | clarified | New formal 'field line' vs 'combined field value' model: the value of a repeated field is all its line values concatenated in order, comma-separated. | 2616 2616 §4.2: "It MUST be possible to combine the multiple header fields into one "field-name: field-value" pair, without changing the semantics of the message" | 9110 §5.2: "combined field value consists of the list of corresponding field line values within that section, concatenated in order" | Header-API semantics: a lookup for a repeated field must yield the ordered comma-joined value (or all lines in order) -- a 2616-era client that returns only the first or last instance silently mis-reads Cache-Control, Vary, Connection, etc. | http1 returns []hpack.HeaderField preserving line order -- correct by construction. Verify the client/ layer semantics helpers (anything that looks up Connection, Transfer-Encoding, Content-Length by name) scan ALL lines, not the first match; noteContentLength/resolveContentLength in http1/conn.go already special-case duplicates -- confirm the same rigor for Connection and Trailer. |
