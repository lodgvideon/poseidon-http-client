# RFC 7540 -> RFC 9113 Delta -- where an HTTP/2 client built to the obsolete spec diverges from the current HTTP/2 slice

_Where an HTTP/2 client built to RFC 7540 diverges from the current RFC 9113. Both quotes verbatim from their source; each delta re-verified by two independent Opus passes (default-refute). Rows flagged VERIFY need a manual source check._

### priority - HTTP/2 priority delta: RFC 7540 dependency/weight tree vs RFC 9113 deprecation

| ID | Change | Summary | RFC 7540 | Current (9113) | Client impact | Reconcile / status |
|----|--------|---------|----------|----------------|---------------|--------------------|
| `priority-1` | deprecated | The entire RFC 7540 Section 5.3 priority signaling scheme (stream dependencies + weights) is deprecated wholesale in RFC 9113. | 7540 RFC 7540 §5.3: "Streams can be prioritized by marking them as dependent on the completion of other streams (Section 5.3.1)." | RFC 9113 §5.3.2: "This update to HTTP/2 deprecates the priority signaling defined in RFC 7540 [RFC7540]." | Silent feature death, not an error: every dependency/weight signal the client sends is legal on the wire but modern RFC 9113 servers are expected to ignore it. A load generator exposing priority knobs gives users a control that does nothing against current servers — misleading benchmark results. | conn/ — Stream.SendHeadersWithPriority and writeHeadersWithPriority are the public carriers of the deprecated signal; docs/CLIENT_GUIDE.md section '4. Request priority (RFC 7540 §5.3)' and client/example_observ_test.go Example_requestPriority advertise it as a live feature. Keep for interop but document as deprecated-per-9113. |
| `priority-2` | deprecated | Priority fields carried in HEADERS frames are deprecated; the rule that priority fields on subsequent HEADERS reprioritize the stream is gone. | 7540 RFC 7540 §6.2: "Prioritization fields in HEADERS frames subsequent to the first on a stream reprioritize the stream (Section 5.3.3)." | RFC 9113 §6.2: "Priority signals in HEADERS frames are deprecated; see Section 5.3.2." | A 7540-era client that sets the PRIORITY flag on HEADERS (initial or subsequent) to steer scheduling gets a no-op. Note the fields themselves stay in the 9113 frame format, so parsing HEADERS with the PRIORITY flag from a peer must be RETAINED — stripping the parse path would break interop with 7540-era peers. | frame/ — writer sets FlagHeadersPriority and encodes E/StreamDep/Weight in framer.go (WriteHeaders slow path); the HEADERS parse path decodes *Priority. Keep both codecs; only the conn/-level sending semantics are vestigial. |
| `priority-3` | deprecated | The PRIORITY frame itself is redefined from 'specifies the sender-advised priority of a stream' to a deprecated legacy frame. | 7540 RFC 7540 §6.3: "The PRIORITY frame (type=0x2) specifies the sender-advised priority of a stream (Section 5.3)." | RFC 9113 §6.3: "The PRIORITY frame (type=0x02) is deprecated; see Section 5.3.2." | Sending standalone PRIORITY frames (e.g. Firefox-style idle-stream priority trees) is pointless against 9113 servers. Receiving them must still work. The client's receive side treating PRIORITY as a no-op is exactly correct under 9113 — that posture is now spec-blessed rather than lazy. | frame/ — Framer.WritePriority exists (framer.go:280); conn/ — OnPriority is deliberately a no-op (conn/coverage_test.go TestHandler_OnPriority_IsNoop already calls it 'deprecated'). Verify no public API encourages sending standalone PRIORITY frames. |
| `priority-4` | removed | The MUST-level rule that a self-dependent stream is a PROTOCOL_ERROR stream error was dropped along with all dependency semantics. | 7540 RFC 7540 §5.3.1: "A stream cannot depend on itself. An endpoint MUST treat this as a stream error (Section 5.4.2) of type PROTOCOL_ERROR." | RFC 9113 §6.3 (absent): "absent" | Over-strict behavior risk: a 7540-conformant client that validates received PRIORITY/HEADERS for self-dependency and sends RST_STREAM(PROTOCOL_ERROR) now kills streams a 9113 peer considers perfectly legal (the dependency field is opaque in 9113). Conversely, dropping the check is now correct, not a conformance gap. | conn/ — confirm the handler's OnPriority/OnHeaders path performs NO self-dependency validation (no-op OnPriority suggests it does not); frame/ — confirm dispatchPriority only length-checks and never inspects StreamDep vs StreamID. If any TestConformance_RFC7540_* test pins the self-dependency error, it now pins obsolete behavior. |
| `priority-5` | removed | All field semantics were stripped: the weight+1 mapping to 1..256, the exclusive-flag meaning, and the proportional-allocation SHOULD exist only in RFC 7540 now. | 7540 RFC 7540 §6.3: "Add one to the value to obtain a weight between 1 and 256." | RFC 9113 §6.3: "Weight: An unsigned 8-bit integer." | The Exclusive/StreamDependency/Weight bytes are now semantically opaque wire filler retained purely for interop. Any client code that computes weights (the +1 mapping), applies §5.3.2's 'Streams with the same parent SHOULD be allocated resources proportionally based on their weight', or documents weight ranges is describing behavior no current spec defines. | frame/ — frame.go's Priority struct doc says 'RFC 7540 §6.3'; check whether Weight is documented as wire-value (0..255) or effective weight (1..256), and whether conn//client/ docs promise proportional scheduling effects (CLIENT_GUIDE §4). |
| `priority-6` | removed | Default priorities (non-exclusive dependency on stream 0, weight 16) were removed, and 9113 explicitly calls those defaults poor-performing and likely unintentional. | 7540 RFC 7540 §5.3.5: "All streams are initially assigned a non-exclusive dependency on stream 0x0." | RFC 9113 §5.3.2: "The defaults described in Section 5.3.5 of [RFC7540] are known to have poor performance under most conditions, and their use is unlikely to be deliberate." | Actively harmful pattern: a 7540 client that EXPLICITLY emits the default (dep=0, wire weight 15 = weight 16) signals 'I implement priorities' while sending a value 9113 flags as known-bad; 9113 also lets servers treat COMPLETE absence of signals as 'client does not implement the feature'. Omitting the PRIORITY flag entirely is now strictly better than sending defaults. | conn/ — check whether SendHeaders (non-priority path) ever auto-fills a default Priority instead of passing nil, and that writeHeadersWithPriority with prio=nil omits the flag (conn/continuation_test.go uses Weight: 15, i.e. the exact known-bad default weight 16); client/ — check the request-priority option's default. |
| `priority-7` | removed | The whole dependency-tree machinery — exclusive insertion, reprioritization moves, idle-stream grouping nodes — was removed from the current spec. | 7540 RFC 7540 §5.3.1: "The exclusive flag causes the stream to become the sole dependency of its parent stream, causing other dependencies to become dependent on the exclusive stream." | RFC 9113 §5.3.2: "The bulk of the text related to priority signals is not included in this document." | Any client-side dependency-tree bookkeeping (tracking parents, applying exclusive re-parenting, sending PRIORITY on idle streams to build grouping nodes) is dead complexity with zero effect on 9113 servers. For a client that never built the tree, this is a no-op — which is the correct end state. | conn/ — confirm no dependency-tree state exists on Conn or Stream (OnPriority no-op implies none); confirm nothing sends PRIORITY frames for idle stream IDs. If absent, this delta is already satisfied — document it as deliberate, not a gap against TestConformance_RFC7540_* expectations. |
| `priority-8` | removed | The SHOULD-level requirements to retain priority state for closed streams (and to size that state to MAX_CONCURRENT_STREAMS) were dropped. | 7540 RFC 7540 §5.3.4: "an endpoint SHOULD retain stream prioritization state for a period after streams become closed." | RFC 9113 (absent): "absent" | No-op for correctness, but a memory-relevant divergence for a pooled, zero-alloc client: any post-close retention of priority state (or handling of PRIORITY frames referencing closed streams as tree updates) is wasted memory and code. Safe to hold zero priority state per stream. | conn/ — verify recycleStream carries no priority-related fields (pooled-stream reset invariant: any per-stream priority field would need explicit reset anyway), and that PRIORITY for an evicted/closed stream ID is silently ignored rather than errored. |
| `priority-9` | added | RFC 9113 points endpoints at a replacement scheme — the Extensible Priorities mechanism ([HTTP-PRIORITY], RFC 9218: Priority header + PRIORITY_UPDATE frame). | 7540 RFC 7540 (absent): "absent" | RFC 9113 §5.3.2: "endpoints are encouraged to use an alternative scheme, such as the scheme described in [HTTP-PRIORITY]." | Capability gap: a pure 7540 client has NO way to express priority that current servers honor. The minimal modern path is sending a 'priority' request header field (needs no new frame support); full parity needs the PRIORITY_UPDATE frame (type 0x10) and SETTINGS_NO_RFC7540_PRIORITIES from RFC 9218. Also note a 9113 peer may send unknown frame type 0x10 — must be ignored, not errored. | frame/ — no PRIORITY_UPDATE (0x10) codec exists; confirm unknown-frame-type handling discards it cleanly. client/ — the request-priority feature could grow a Priority-header variant. hpack/ — nothing needed ('priority' is an ordinary header field). |
| `priority-10` | reworded_same | The mandatory PRIORITY wire handling is retained verbatim for interop: stream-ID 0 is a connection PROTOCOL_ERROR, length != 5 is a stream FRAME_SIZE_ERROR, sendable in any stream state, never between header-block frames. | 7540 RFC 7540 §6.3: "A PRIORITY frame with a length other than 5 octets MUST be treated as a stream error (Section 5.4.2) of type FRAME_SIZE_ERROR." | RFC 9113 §6.3: "A PRIORITY frame with a length other than 5 octets MUST be treated as a stream error (Section 5.4.2) of type FRAME_SIZE_ERROR." | Load-bearing no-op: 'priorities are deprecated' does NOT license removing the PRIORITY codec or its error handling. A client that strips PRIORITY parsing breaks against 7540-era peers; one that drops the length/stream-0 checks under-enforces both specs. These MUSTs survive unchanged in 9113. | frame/ — dispatchPriority's length check (ErrPriorityWrongLength, framer.go:588) stays. VERIFY the stream-ID-0 -> connection error PROTOCOL_ERROR check exists somewhere (frame/ dispatch or conn/ handler) — dispatchPriority appears to length-check only; a missing ID-0 check is a gap against BOTH specs. Also verify PRIORITY between HEADERS and CONTINUATION is rejected as a connection error (§4.3/§6.2 END_HEADERS rule). |
| `priority-11` | clarified | RFC 9113 states explicitly that sending/receiving PRIORITY never affects stream state, replacing 7540's softer note about frames arriving after processing completes. | 7540 RFC 7540 §6.3: "Note that this frame could arrive after processing or frame sending has completed, which would cause it to have no effect on the identified stream." | RFC 9113 §6.3: "Sending or receiving a PRIORITY frame does not affect the state of any stream (Section 5.1)." | Guardrail made explicit: PRIORITY for an idle, closed, unknown, or already-evicted stream must be tolerated silently — it must not create stream objects, transition state machines, count against concurrency limits, or trigger errors. A 7540 client that instantiated tracking state on PRIORITY-for-idle-stream (per §5.3.4 grouping nodes) is now doing spec-less work and risks unbounded state from a hostile peer. | conn/ — the no-op OnPriority satisfies this by construction; confirm the frame-dispatch path before OnPriority does not touch the stream registry or allocate per-stream state for unknown IDs (peer-input policy: charge what memory retains). |

### starting - RFC 7540 §3 → RFC 9113 §3 delta: connection bootstrap, h2c Upgrade, HTTP2-Settings

| ID | Change | Summary | RFC 7540 | Current (9113) | Client impact | Reconcile / status |
|----|--------|---------|----------|----------------|---------------|--------------------|
| `starting-1` | removed | The entire HTTP/1.1 Upgrade (h2c) bootstrap for "http" URIs (7540 §3.2) is deleted; the h2c token is formally deprecated. | 7540 RFC 7540 §3.2: "making an HTTP/1.1 request that includes an Upgrade header field with the "h2c" token" | RFC 9113 §3.1: "This usage was never widely deployed and is deprecated by this document." | A 7540-era client that sends Upgrade: h2c gets served plain HTTP/1.1 by 9113 servers — a silent permanent downgrade to h1, wasted request, and dead upgrade-handling code (101 parsing, Upgrade token matching). Cleartext h2 must now go straight to the connection preface. | conn/ handshake path + client/ H1/ALPN transports: confirm no Upgrade:h2c code path exists anywhere (grep http1/ and client/ for "h2c" and "Upgrade"); if the repo never implemented it, mark N/A-by-design in docs/RFC_COVERAGE.md rather than leaving the 7540 §3.2 row implied. |
| `starting-2` | removed | The HTTP2-Settings header field (7540 §3.2.1) — base64url SETTINGS payload, exactly-one requirement, Connection option, implicit ACK via 101 — is deleted and deprecated. | 7540 RFC 7540 §3.2.1: "A request that upgrades from HTTP/1.1 to HTTP/2 MUST include exactly one "HTTP2-Settings" header field." | RFC 9113 §3.1: "The same applies to the HTTP2-Settings header field, which was used with the upgrade to "h2c"." | A client that generates HTTP2-Settings now emits a deprecated connection-specific field no server should honor; any base64url-SETTINGS-payload encoder and the '101 implies SETTINGS ACK' logic are dead code. Initial settings are conveyed ONLY by the preface SETTINGS frame. | http1/ + hpack/: verify no code emits or parses "HTTP2-Settings" and no base64url SETTINGS serialization exists; conn/: verify initial settings travel only in the handshake SETTINGS frame and are ACKed per §6.5.3, never implicitly. |
| `starting-3` | removed | Post-upgrade stream 1 semantics gone: no rule assigning the upgrading HTTP/1.1 request stream id 1, implicitly half-closed (client), carrying the response. | 7540 RFC 7540 §3.2: "The HTTP/1.1 request that is sent prior to upgrade is assigned a stream identifier of 1" | RFC 9113 §3: "absent" | Any special-casing that reserves stream 1 as response-only/half-closed is now a bug: on ALPN or prior-knowledge connections the client's first real request must get id 1 as an ordinary fully-open stream. A 7540 client that skips id 1 wastes stream-id space; one that treats id 1 as half-closed breaks its first request. | conn/ stream-ID allocation (B.2.1 deferred allocation in SendHeaders): confirm the first stream is plain id 1 with no reservation or pre-half-closed state; frame/: no special framing for stream 1. |
| `starting-4` | removed | The 'send client preface upon receipt of a 101 response' trigger is deleted; the preface is now unconditionally the first application data octets of a connection. | 7540 RFC 7540 §3.5: "The client sends the client connection preface immediately upon receipt of a 101 (Switching Protocols) response" | RFC 9113 §3.4: "The client sends the client connection preface as the first application data octets of a connection." | A client that gates preface transmission on any HTTP/1.1 response deadlocks against a 9113 server (both sides waiting). Also note the generalization from 'a TLS connection' to 'a connection' — the same first-octets rule now covers prior-knowledge cleartext identically. | conn/ handshake: verify the 24-octet magic + SETTINGS is written unconditionally at connection start, never conditioned on reading any bytes first; conformance test for this should cite 9113 §3.4, not 7540 §3.5. |
| `starting-5` | tightened | Discovery for "http" URIs no longer has an in-band mechanism: prior (out-of-band) knowledge is the only route to cleartext HTTP/2. | 7540 RFC 7540 §3: "Discovery for "http" URIs is described in Section 3.2." | RFC 9113 §3: "HTTP/2 support for "http" URIs can only be discovered by out-of-band means and requires prior knowledge of the support" | For http:// targets a 7540 client 'probes' with Upgrade and falls back; a 9113 client must either be configured for prior-knowledge h2c (preface-first) or stay on HTTP/1.1. Auto-negotiation attempts on cleartext are over-eager, non-conformant noise. | client/ transport selection (H1 vs single-conn/pool): confirm cleartext h2 is opt-in prior-knowledge only and the H1 transport never attempts version upgrade; conn/ needs no change if it already assumes preface-first. |
| `starting-6` | security_hardening | The "https" bootstrap now references TLS 1.3 ([TLS13]) instead of TLS 1.2 ([TLS12]) as the base TLS citation. | 7540 RFC 7540 §3.3: "A client that makes a request to an "https" URI uses TLS [TLS12] with the application-layer protocol negotiation (ALPN) extension" | RFC 9113 §3.2: "A client that makes a request to an "https" URI uses TLS [TLS13] with the ALPN extension [TLS-ALPN]." | TLS 1.2 remains permitted (9113 §9.2 sets the floor), but the reference profile is now TLS 1.3. A client whose tls.Config caps MaxVersion at 1.2, or whose 7540-derived cipher/feature checks assume TLS 1.2 semantics, is behind the current spec's baseline. | client/ ALPN transport TLS config (and the gosec G402 opt-in noted in CLAUDE.md): confirm TLS 1.3 is negotiable by default and nothing pins TLS 1.2; conn/ handshake must not assume TLS-1.2-only artifacts. |
| `starting-7` | moved | Section renumbering after §3.2's deletion: 7540 §3.3→9113 §3.2 (https), §3.4→§3.3 (prior knowledge), §3.5→§3.4 (connection preface); §3.2/§3.2.1 have no 9113 counterpart. | 7540 RFC 7540 §3.5: "3.5. HTTP/2 Connection Preface" | RFC 9113 §3.4: "3.4. HTTP/2 Connection Preface" | No wire change, but every citation keyed on 7540 §3.x is now off by one (or dangling for §3.2/§3.2.1). This repo's TestConformance_RFC7540_Sec* names and the section-keyed docs/RFC_COVERAGE.md matrix cite the obsolete numbering; the conformance-gate greps for the RFC7540 prefix. | conn/ conformance test names + docs/RFC_COVERAGE.md: when migrating the gate to RFC 9113, remap §3 rows (3.3→3.2, 3.4→3.3, 3.5→3.4) and retire any 7540 §3.2/3.2.1 rows explicitly rather than renumbering them. |
| `starting-8` | reworded_same | Prior-knowledge text drops the ALT-SVC example and rewrites the client's 'MUST send preface, MAY send frames' as descriptive prose; the preface obligation survives via §3.4. | 7540 RFC 7540 §3.4: "A client MUST send the connection preface (Section 3.5) and then MAY immediately send HTTP/2 frames to such a server" | RFC 9113 §3.3: "can establish a TCP connection and send the connection preface (Section 3.4) followed by HTTP/2 frames" | No behavioral change — 9113 §3.4 still requires each endpoint to send a preface, and 'connections over TLS MUST use protocol negotiation in TLS' is retained verbatim in §3.3. Impact is purely on traceability: a checklist row anchored to the 7540 §3.4 client MUST must re-anchor to 9113 §3.4's endpoint requirement. | docs/RFC_COVERAGE.md only: re-point the prior-knowledge preface row at 9113 §3.4; no conn/ code change expected — verify its existing preface test doesn't cite the 7540 §3.4 MUST as its normative source. |

### fields - RFC 7540 → RFC 9113 delta: field validity, pseudo-headers, field ordering

| ID | Change | Summary | RFC 7540 | Current (9113) | Client impact | Reconcile / status |
|----|--------|---------|----------|----------------|---------------|--------------------|
| `fields-1` | security_hardening | New mandatory octet-level check: field values must not contain NUL, CR, or LF; violation makes the message malformed. | 7540 RFC 7540 §8.1.2 / §8.1.2.6: "absent" | RFC 9113 §8.2.1: "A field value MUST NOT contain the zero value (ASCII NUL, 0x00), line feed (ASCII LF, 0x0a), or carriage return (ASCII CR, 0x0d)" | A 7540-era client silently accepts response header values carrying CR/LF/NUL that HPACK (especially Huffman) can legally convey. That is a request/response-smuggling and header-injection hole the moment values are logged, surfaced to callers, or re-serialized onto HTTP/1.1 (this repo has an http1/ stack and load-gen forwarding use cases). Under 9113 the client MUST treat such a response as malformed (stream error PROTOCOL_ERROR, response not accepted) and MUST NOT generate such values in requests. | hpack/ (decoder emits raw octets — decide whether validation lives in decode or in the header-assembly callback) + conn/ (malformed → RST PROTOCOL_ERROR path for received HEADERS; reject on send). Check both request-build and response-accept sides. |
| `fields-2` | tightened | Field-name validation widened from 'no uppercase' to full octet ranges: 0x00-0x20, 0x41-0x5a, 0x7f-0xff all forbidden. | 7540 RFC 7540 §8.1.2: "A request or response containing uppercase header field names MUST be treated as malformed" | RFC 9113 §8.2.1: "A field name MUST NOT contain characters in the ranges 0x00-0x20, 0x41-0x5a, or 0x7f-0xff (all ranges inclusive)." | A client that only checks for A-Z in names (the sole 7540 rule) is under-strict: names containing control characters, SP, DEL, or high-bit octets must now also make the message malformed. Silent acceptance of e.g. a name with an embedded 0x00 or 0x20 is exactly the smuggling vector 9113 calls out. Empty impact on well-behaved servers, real impact against adversarial/fuzzed peers. | conn/ header validation (and/or hpack/ decode hook) — verify the name check is a range check per 9113, not just an uppercase check. Wire a fuzz/negative test that pushes these octets through HPACK Huffman. |
| `fields-3` | added | New rule: non-pseudo field names must not contain a colon. | 7540 RFC 7540 §8.1.2: "absent" | RFC 9113 §8.2.1: "field names MUST NOT include a colon (ASCII COLON, 0x3a)." | 0x3a is NOT excluded by the fields-2 range check (it sits in the allowed 0x21-0x40 band), so this needs its own branch: a name like "x:status" or "foo:bar" must be rejected as malformed. Guards against pseudo-header spoofing and against colon-as-delimiter confusion when downgrading to HTTP/1.1. A 7540 client has no reason to have this check at all. | conn/ pseudo-header/regular-field classifier — confirm names starting with ':' are matched only against the defined pseudo-header set, and any other position of ':' in a name is malformed. |
| `fields-4` | added | New rule: field values must not start or end with SP/HTAB. | 7540 RFC 7540 §8.1.2: "absent" | RFC 9113 §8.2.1: "A field value MUST NOT start or end with an ASCII whitespace character (ASCII SP or HTAB, 0x20 or 0x09)." | Two-sided: (1) receive — a response value with leading/trailing SP/HTAB must be treated as malformed, where a 7540 client passes it through; (2) send — caller-supplied header values with padding (common in hand-built load-test headers) must be rejected or normalized before encoding, else 9113-strict servers will 400/RST requests that used to work. | conn/ (receive-side malformed check) + the request-building entry point (client/ hands headers to conn/) for send-side validation. Note per 9113 the check is on the generic syntax only — do not trim silently if you want strict conformance on generate. |
| `fields-5` | added | New explicit prohibition: the same pseudo-header field name must not appear twice in a field block. | 7540 RFC 7540 §8.1.2.1: "absent" | RFC 9113 §8.3: "The same pseudo-header field name MUST NOT appear more than once in a field block." | 7540 only required 'exactly one valid value' for the mandatory request pseudo-headers; it had no general duplicate rule, so a 7540 client typically takes first-wins or last-wins on a duplicated :status without error. Under 9113 a response with two :status pseudo-headers (classic desync primitive) MUST be treated as malformed. Send side: the client must also never emit a duplicate pseudo-header. | conn/ response pseudo-header parsing — needs a seen-set per field block (HEADERS + CONTINUATION assembly), covering trailers too (where any pseudo-header is already malformed in both specs). Add a negative conformance test keyed to 9113 §8.3. |
| `fields-6` | clarified | :status is now explicitly required in interim (1xx) responses as well. | 7540 RFC 7540 §8.1.2.4: "This pseudo-header field MUST be included in all responses; otherwise, the response is malformed" | RFC 9113 §8.3.2: "This pseudo-header field MUST be included in all responses, including interim responses; otherwise, the response is malformed" | A 7540-era client that treats 1xx HEADERS as a skippable oddity may not validate them at all (this repo's HTTP/2 stack historically had zero 1xx handling — known sibling-divergence risk vs the H3 stack). Under 9113 an interim response without :status, or with regular fields but no pseudo-headers, must be treated as malformed rather than silently ignored. | conn/ — check how HEADERS frames before the final response are classified: they must go through the same pseudo-header validation (presence, ordering, duplicates) as final responses. Cross-check against http3/'s 1xx handling for divergence. |
| `fields-7` | tightened | Client use of :authority upgraded SHOULD → MUST (and :authority must be omitted when there is no authority information). | 7540 RFC 7540 §8.1.2.3: "Clients that generate HTTP/2 requests directly SHOULD use the ":authority" pseudo-header field instead of the Host header field." | RFC 9113 §8.3.1: "Clients that generate HTTP/2 requests directly MUST use the ":authority" pseudo-header field to convey authority information" | A 7540 client that conveys the target host via a Host header field (with no :authority) was SHOULD-conformant; under 9113 it is non-conformant and 9113-strict servers/intermediaries may reject it. Conversely, 9113 adds 'unless there is no authority information to convey (in which case it MUST NOT generate ":authority")' — near no-op for a load generator hitting http/https URLs, but the invariant should be encoded. | conn/ request pseudo-header construction (SendHeaders path) plus wherever client/ maps a URL to pseudo-headers — verify :authority is always emitted from the URL authority and Host is not used as the carrier. |
| `fields-8` | added | New prohibition: a request's Host header must not differ from :authority (servers SHOULD reject mismatches as malformed). | 7540 RFC 7540 §8.1.2.3: "absent" | RFC 9113 §8.3.1: "Clients MUST NOT generate a request with a Host header field that differs from the ":authority" pseudo-header field." | If a caller supplies an explicit Host header (common in load testing for vhost fanout / Host-spoofing scenarios) and the client also sets :authority from the URL, a mismatch that 7540 tolerated now (a) violates a client MUST and (b) is likely to draw 400/RST from 9113 servers, since they SHOULD treat the request as malformed. The client library should validate/normalize caller-supplied Host against :authority or document that it forwards the mismatch deliberately. (Related recipient-side rule — Host ignored when :authority present — only matters if PUSH_PROMISE requests are ever validated.) | client/ (caller-supplied header pass-through policy) + conn/ (where pseudo-headers and regular fields merge into one HEADERS block). Decide and document the load-generator escape hatch, since intentional Host mismatch is a legitimate test scenario. |
| `fields-9` | added | New SHOULD: validate names/values against RFC 9110 §5.1/§5.5 generic syntax; plus note that semantically invalid values are NOT malformed. | 7540 RFC 7540 §8.1.2: "absent" | RFC 9113 §8.2.1: "HTTP/2 implementations SHOULD validate field names and values according to their definitions in Sections 5.1 and 5.5 of [HTTP]" | Beyond the four mandatory octet checks, full token/field-value grammar validation is now recommended. Also load-bearing in the other direction: 9113's note says 'Field values that are not valid according to the definition of the corresponding field do not cause a request to be malformed' — so a client must not over-reject, e.g. a garbage Content-Type is not a protocol-level malformed message. 9113 notes full §5.1/§5.5 validation plus an uppercase check subsumes the mandatory list. | conn/ — decide policy tier: mandatory octet checks (fields-1..4) as MUST, optional strict-mode flag for full 9110 grammar. Keep semantic-value errors out of the RST path. |
| `fields-10` | tightened | Connection-specific header removal by intermediaries upgraded SHOULD → MUST, with the prohibited set now normatively enumerated. | 7540 RFC 7540 §8.1.2.2: "Such intermediaries SHOULD also remove other connection-specific header fields, such as Keep-Alive, Proxy-Connection, Transfer-Encoding, and Upgrade" | RFC 9113 §8.2.2: "An intermediary transforming an HTTP/1.x message to HTTP/2 MUST remove connection-specific header fields as discussed in Section 7.6.1 of [HTTP]" | This repo is a client, not an intermediary, so the MUST itself is a near no-op — but the prohibited set is now definitionally pinned (Connection, Proxy-Connection, Keep-Alive, Transfer-Encoding, Upgrade; TE allowed only with value "trailers", unchanged). The receive-side rule (any message containing them is malformed) exists in both specs; verify the client's malformed check actually enumerates this exact set on responses and that the send-side blocklist rejects caller-supplied connection-specific headers rather than passing them through. | conn/ — send-side blocklist and receive-side malformed detection; confirm the list matches 9113's enumeration exactly and the TE=trailers carve-out applies to requests only (mirror of the recent http3 fix in commit 9e1b62d). |
