# Ревью блокировок на потоках данных

Дата: 2026-09-13. Ревизия: `claude/wonderful-albattani-zigj1t` (ветка от `main`,
цикл v0.13.0). Стенд замеров: Linux, `go1.25.13 linux/amd64`, Intel Xeon @ 2.80 GHz,
4 vCPU.

Цель документа — найти **точки сериализации на путях данных** (где горутина
останавливается и ждёт другую горутину, а не сеть) и дать по каждому потоку
дорожную карту. Это ревью производительности под профиль нагрузочного
генератора: много одновременных запросов, быстрый peer, цель — насытить канал.

---

## 0. Резюме

| # | Поток | Главная блокировка | Замер | Приоритет |
|---|---|---|---|---|
| **F1** | HTTP/2 egress (запрос) | `Conn.wmu` удерживается через `write(2)`/TLS-запись | **88.5 % всего block-time**, 100 % mutex-профиля | **P0** |
| **F2** | HTTP/2 ingress (ответ) | одна reader-горутина на соединение; overflow канала = RST(CANCEL) | потолок ~1 ядро/conn; потери под всплеском | **P1** |
| **F3** | Outbound flow control (upload) | `fcOutCond.Broadcast()` на каждый WINDOW_UPDATE | O(N) пробуждений на кадр | **P1** |
| **F4** | Пул соединений (H2/H1/H3) | актор-горутина, unbuffered `acquireCh` | 9.6 мкс/запрос blocked | **P2** |
| **F5** | HTTP/1.1 exchange | watchdog: 2 рандеву на **каждый** блокирующий I/O | 2 переключения контекста на чанк тела | **P2** |
| **F6** | QUIC datagram in/out | **один `Conn.mu` на всё**, включая `sendto`; `Send` держит его на весь payload | нарушение собственного инварианта §3.2 | **P1** |
| **F7** | HTTP/3 QPACK | `encMu` сериализует кодирование заголовков всех Do | CPU-bound под общим локом | **P2** |
| **F8** | Rate limiter | глобальный мьютекс + `time.After` на каждого ждущего | thundering herd | **P2** |
| **F9** | Managed pool / resolver | `RWMutex` + 2 аллокации на запрос | cache-line contention | **P3** |

**Главный вывод.** Узкое место одно и оно уже измерено и уже решено —
но решение недоступно из публичного API. `conn.SendBatch` (батч из 32 запросов
под одним взятием `wmu`) даёт **7.3× по латентности и 23× по числу write-syscall'ов**
против обычного пути. `client.Do` этим не пользуется, а `GroupCommit` выключен
по умолчанию.

## 2. Методика

Все цифры получены на этой машине, командами из репозитория:

```bash
# профили contention на «быстром peer» (zero-alloc framer) — режим насыщения
go test ./conn/ -run=NONE -bench='BenchmarkLoadGen_Unary_C64$' -benchtime=20000x \
  -mutexprofile=mutex.out -blockprofile=block.out

# полный клиентский путь против настоящего net/http2 сервера
go test ./client/ -run=NONE -bench='BenchmarkGCPool_Off_C8_W64$' -benchtime=20000x \
  -mutexprofile=... -blockprofile=...
```

**Два режима, и их нельзя путать.** Против медленного peer'а (реальный
`net/http2`-сервер, `client/`-бенчмарк) 73 % block-time — это `Stream.recv`,
то есть честное ожидание сети; `wmu` почти не виден (mutex-профиль всего 67 мс).
Против быстрого peer'а (`conn/`-бенчмарк, режим насыщения канала — целевой для
нагрузочного генератора) картина переворачивается: `wmu` — 88.5 %.

Оба числа верны. Второй режим — тот, ради которого библиотека написана.

## F1. HTTP/2 egress — `Conn.wmu` удерживается через syscall

### Что происходит

`conn/conn.go:142` — `wmu sync.Mutex // serializes all writes to fr`. Все
записи кадров любого стрима соединения проходят через него. Критическая
секция включает **саму запись в сокет**: `flushWrite()` (`conn/conn.go:374`)
вызывает `bufio.Writer.Flush()` → `tls.Conn.Write` → `write(2)`, и всё это —
под `wmu`.

`writeDataVec` (`conn/datav.go:315-366`) делает так на **каждый DATA-кадр**:

```go
for v.rem > 0 {
    c.wmu.Lock(); c.flushWrite(); c.wmu.Unlock()   // flush перед парковкой
    n, _ := c.acquireSendCredits(ctx, ...)          // может заблокироваться
    c.wmu.Lock(); c.emitDataV(...); c.flushWrite(); c.wmu.Unlock()
}
```

Это осознанное решение: держать `wmu` во время ожидания кредита — дедлок
(peer не увидит кадр, значит не пришлёт WINDOW_UPDATE). Но следствие —
`writeDataVec` намеренно обходит group-commit (`flushWrite`, а не `commitFrame`),
то есть **каждый DATA-кадр = отдельный syscall под глобальным локом соединения**.

### Доказательство

Block-профиль, `Unary_C64`, 20000 итераций, 64 горутины, суммарно 34.75 с
заблокированного времени:

```
88.51%  sync.(*Mutex).Lock                     ← wmu, flat
  52.39%    ← conn.(*Conn).writeHeadersWithPriority
  36.06%    ← conn.(*Conn).writeDataVec
 8.28%  runtime.selectgo                       ← Stream.recv, честное ожидание сети
```

Mutex-профиль — **100 % contention на этом же мьютексе** (28.08 с):
60.30 % headers / 39.57 % data.

Бенчмарки (ns/op и syscall'ы на запрос):

| bench | writes/req | ns/op | к базе |
|---|---|---|---|
| `Unary_C1` | 2.002 | 79754 | — |
| `Unary_C16` | 2.002 | 32045 | — |
| `Unary_C64` | 2.002 | **25273** | 1.00× |
| `Unary_C256` | 2.002 | 20130 | 1.26× |
| `Unary_C64` + `GroupCommit` | 1.235 | 16713 | 1.51× |
| `HeadersOnly_C64` + `GroupCommit` | 0.208 | 5651 | — |
| **`Batch32_C64`** (`SendBatch`) | **0.0875** | **3472** | **7.28×** |

`SendBatch` берёт `wmu` один раз на 32 запроса и делает один flush.
Результат: **23× меньше write-syscall'ов, 7.3× меньше ns/op.**
Согласуется с профилем CPU из `docs/H2_RAW_FRAMES_DESIGN.md` §7a:
61.7 % CPU — syscall'ы, из них 44.2 % — записи в сокет; 22.7 % — планировщик
(park/unpark вокруг них).

### Почему это не используется

- `conn.SendBatch` (`conn/batch.go:153`) — **ни одного вызова вне тестов**.
  Из `client.Do` недостижим.
- `ConnOptions.GroupCommit` (`conn/options.go:112`) — **по умолчанию выключен**,
  и на unary-трафике даёт только 1.235 writes/req, потому что DATA-путь его
  обходит (см. выше).

То есть реальный пользователь `client.Do` сегодня получает 2.002 writes/req —
худшую из измеренных точек.

| Шаг | Что делаем | Критерий проверки | Оценка |
|---|---|---|---|

## F2. HTTP/2 ingress — одна reader-горутина, потери при переполнении

### Что происходит

`readerLoop` (`conn/conn.go:2022`) — **одна горутина на соединение** делает всё:
`ReadFrame` → HPACK-декод → валидацию → доставку события в канал стрима.
При 100+ активных стримах на соединении это жёсткий потолок в одно ядро
на приём.

Доставка намеренно неблокирующая (`pushLocked`, `conn/stream.go:654`):

```go
select {
case s.events <- e:
    return true
default:
}
// канал полон → закрываем стрим и шлём RST_STREAM(CANCEL)
```

Это правильное решение для reader'а (медленный потребитель не должен
останавливать всё соединение), но **бэкпрешер здесь = потеря запроса**,
а не замедление. `StreamEventBuffer` по умолчанию 8 (`conn/options.go:246`);
`client` поднимает его до бюджета (`client.go:299`, минимум 16).

### Влияние

- Потолок приёма — одно ядро на соединение. Для генератора, который держит
  мало соединений и много стримов, это ограничение раньше, чем сеть.
- Всплеск ответов при занятом потребителе → RST(CANCEL) → запрос помечается
  как сбойный. В отчёте нагрузочного теста это выглядит как ошибка сервера,
  хотя это переполнение локального буфера.

### Дорожная карта F2

| Шаг | Что делаем | Критерий проверки | Оценка |
|---|---|---|---|
| **F2.1** | Метрика переполнения: счётчик `StreamEventOverflow` в `ConnStats`/`Metrics`, чтобы отличать «сервер сбросил» от «мы не успели вычитать». | Тест: медленный потребитель → счётчик растёт, а `RequestsErrored` объяснён | S |
| **F2.2** | Sink-режим приёма (`DiscardResponseBody` / callback вместо канала) — убирает hop «слаб → канал → горутина» для запросов, которым тело не нужно. §7a отвергает это как *перф*-фичу (~1 %), но как **эргономика + отсутствие горутины на запрос** аргумент остаётся. | Бенчмарк без горутины на запрос; доля `runtime.schedule` падает | M |
| **F2.3** | Вынести HPACK-декод и валидацию из reader-горутины в пул воркеров по стримам. Порядок HPACK-декода сохранять обязан — значит декод остаётся, а выносится только валидация + сборка события. | `conn`-бенчмарк на 256 стримах: приём масштабируется > 1 ядра | L |
| **F2.4** | Адаптивный `StreamEventBuffer`: расти при переполнении до потолка байтового бюджета вместо RST. | Под всплеском 0 RST(CANCEL) при том же бюджете памяти | M |

## F3. Outbound flow control — `Broadcast` вместо адресного пробуждения

### Что происходит

`acquireSendCredits` (`conn/conn.go:1387`) паркует писателя на
`fcOutCond.Wait()`. Будят его через `fcOutCond.Broadcast()` — и делают это
**на каждый входящий WINDOW_UPDATE, включая per-stream** (`conn/conn.go:1501`):

```go
s.mu.Lock(); s.sendWindow = int32(newVal); s.mu.Unlock()
c.fcOutMu.Lock()
c.fcOutCond.Broadcast()      // будим ВСЕХ, хотя окно выросло у ОДНОГО стрима
c.fcOutMu.Unlock()
```

При N припаркованных писателей один WINDOW_UPDATE = N пробуждений, из
которых N−1 сразу засыпают обратно, перехватив `fcOutMu` и `s.mu`.
`Broadcast` вызывается из 9 мест (`conn/conn.go:631,726,1456,1478,1501,1689,1786,2182,2192`).

### Когда это больно

На unary-трафике (тело 64 байта) окна не исчерпываются — в моём профиле
`fcOutCond` не виден вовсе. Проблема проявляется на **upload-нагрузке**:
connection-level send-окно стартует с 65535 байт (RFC-обязательное), и
при заливке тел оно вычерпывается за миллисекунды. Дальше каждый
WINDOW_UPDATE будит весь набор писателей.

Это O(N) на кадр при N стримах, и вдобавок разбуженные толпой писатели
конкурируют за `fcOutMu`, который в этот момент держит reader — то есть
замедляется и приём.

### Дорожная карта F3

| Шаг | Что делаем | Критерий проверки | Оценка |
|---|---|---|---|
| **F3.1** | Бенчмарк upload-профиля (`BenchmarkLoadGen_Upload_*`, тела 256 КиБ, C64) + block-профиль. Без него шаги ниже не измеримы. | Профиль показывает долю `acquireSendCredits`; это базовая линия | S |
| **F3.2** | Per-stream ожидание: заменить общий `sync.Cond` на канал-сигнал на стрим (как `quic`'s cap-1 `s.ready`). Per-stream WINDOW_UPDATE будит ровно одного. | Число пробуждений на WINDOW_UPDATE: N → 1; ns/op upload-бенча | M |
| **F3.3** | Conn-level WINDOW_UPDATE оставить broadcast'ом, но будить в FIFO-порядке очереди ожидающих, а не всех — иначе на conn-окне остаётся та же толпа. | Честность: тест на отсутствие голодания стрима | M |
| **F3.4** | Поднять стартовое conn-окно через SETTINGS/WINDOW_UPDATE сразу после handshake (сейчас auto-tune поднимает только recv-окна; send-окно диктует peer, но мы можем запросить больше на приём и тем ускорить peer'а). | Upload-бенч: время до насыщения окна растёт | S |

## F4. Пул соединений — актор-горутина на каждый acquire

### Что происходит

`internal/poolcore/pool.go:246` — `Pool.run()` — **одна горутина**, обрабатывающая
`acquireCh` / `releaseCh` / `dialDoneCh` / `statsCh` / тик. `acquireCh`
**небуферизованный** (`pool.go:182`). Каждый `Acquire` (`pool.go:858`) — это
рандеву с актором плюс ответ по буферизованному каналу: минимум два
переключения контекста на запрос.

`PickLeastLoaded` (`pool.go:626`) — линейный скан списка соединений с
ротирующим курсором и ранним выходом на первом idle. Амортизированно дёшево,
но худший случай O(N) **внутри единственной горутины-актора**.

Та же схема продублирована трижды: `poolcore` (H2), `client/h1_pool.go` (H1),
`client/h3_pool.go` (H3).

### Доказательство

Block-профиль клиентского пути (`GCPool_Off_C8_W64`, 20000 запросов):

```
Pool.Acquire  192.1 ms  (1.29 % block-time)  → 9.6 мкс/запрос заблокированного времени
Pool.Release   37.7 ms  (0.25 %)             → 1.9 мкс/запрос
Pool.run      273.9 ms  (1.84 %)             → сам актор
```

Против медленного peer'а это тонет в ожидании сети. В режиме насыщения
(12.7 мкс/op на этом бенче) 11.5 мкс суммарной блокировки на запрос —
уже сопоставимая величина.

### Дорожная карта F4

| Шаг | Что делаем | Критерий проверки | Оценка |
|---|---|---|---|
| **F4.1** | Fast path мимо актора: атомарный «дежурный» слот с наименее нагруженным живым соединением; `Acquire` пробует CAS на нём и идёт к актору только при промахе. Актор остаётся владельцем состояния и обновляет слот. | `Pool.Acquire` block-time на запрос: 9.6 мкс → < 1 мкс; гонок нет под `-race` | M |
| **F4.2** | Буферизовать `acquireCh` (сейчас 0) — снимает один context switch на запрос при занятом акторе. Осторожно: меняет семантику отказа от ожидания (первый select в `Acquire`). | Тест на abandonment-пути (`recycle`) зелёный; block-time падает | S |
| **F4.3** | Шардировать пул по P (`runtime.GOMAXPROCS`): N акторов, каждый со своим подмножеством соединений. Снимает единственную горутину как потолок. | Масштабирование req/s по числу ядер на `GCPool_*_C64` | L |
| **F4.4** | Свести три копии актора (`poolcore`/`h1_pool`/`h3_pool`) в одну — иначе каждое улучшение делается трижды и расходится. ADR-0002 уже объясняет, почему `poolcore` не generic; решение — вынести общий цикл, оставив типизированный слой тонким. | Диффы h1/h3-пулов не содержат копии цикла; все тесты зелёные | L |

## F5. HTTP/1.1 — watchdog-рандеву на каждый блокирующий I/O

### Что происходит

`http1` однопоточен внутри exchange, поэтому отмену контекста реализует
watchdog-горутина (`http1/conn.go:709`), которая «сдвигает дедлайн сокета в
прошлое». Взведение и снятие — два рандеву по **небуферизованным** каналам
(`armWatch` :736, `disarmWatch` :756):

```
idle --armCh--> watching --disarmCh--> idle
```

Небуферизованный send завершается только когда получатель выбрал ветку select.
То есть каждое взведение и каждое снятие = передача управления другой горутине.

Взводится это на **каждом** блокирующем вызове:

- `writeHead` (`:1247`), `WriteBody` (`:1265`) — на каждый кусок тела;
- `ReadResponse` (`:1434`);
- **`ReadBodyChunk` (`:2362`) — на каждый чанк тела.**

Тело в 1 МиБ при чтении по 16 КиБ — 64 чанка — **128 рандеву**.

### Оценка

Это уже оптимизация: предыдущая версия аллоцировала горутину + два канала
на вызов, и была вторым-третьим местом по байтам аллокаций в `http1`.
Текущая форма не аллоцирует, но платит планировщиком.

### Дорожная карта F5

| Шаг | Что делаем | Критерий проверки | Оценка |
|---|---|---|---|
| **F5.1** | Сузить условие взведения. `armDeadline` (`:789`) взводит watchdog **безусловно**, даже когда `ctx` несёт дедлайн и тот уже выставлен на сокет — комментарий это оговаривает («не else-ветка»), потому что отмена и дедлайн не альтернативы. ## F6. QUIC — один мьютекс на всё, удерживаемый через `sendto`

### Что происходит

`quic/conn.go:36-42`:

```go
// mu guards ALL Conn mutable state and the wire (every pc.Write).
mu sync.Mutex
```

Один `sync.Mutex` (не RWMutex — приём мутирует состояние отправки) закрывает:
приём и разбор датаграмм, AEAD, ACK-трекинг, loss detection, congestion control,
**и запись в сокет**.

`Poll` (`quic/conn_recv.go:95-155`) сделан аккуратно: блокирующий `pc.Read`
выполняется **с отпущенным локом**, таймстемп RTT берётся после
переполучения лока. Это правильно.

Но `Stream.Send` (`quic/send.go:35`) — нет:

```go
func (s *Stream) Send(data []byte, fin bool) (int, error) {
    s.conn.mu.Lock()
    defer s.conn.mu.Unlock()
    return s.sendLocked(data, fin)   // цикл по ВСЕМУ payload
}
```

`sendLocked` крутит цикл `writeStreamFrame` → `addToBatch` по всему payload;
`addToBatch` сбрасывает батч каждые 64 сегмента (`quic/gso.go:21`) и продолжает.
`Send(1 МиБ)` — это ~870 операций seal и ~14 `WriteGSO`-syscall'ов **без
единого отпускания `c.mu`**.

### Почему это findings, а не «так задумано»

`docs/HTTP3_DESIGN.md` §3.2 формулирует инвариант прямым текстом:

> **RTT-skew rule (from review, folded in):** `Do` critical sections must be
> **per-packet** — `Send` releases `c.mu` between `writeStreamFrame`/seal
> iterations and never holds it across a whole `sendAll`.

Реализация этому не соответствует. Дизайн-док описывает `sendAll` (уровень
http3) — и там действительно есть отпускание между вызовами `Send`
(`http3/client.go:629`), но **внутри одного `Send`** лок удерживается на весь
переданный буфер. Для `Do` с телом это весь request body одним вызовом.

### Последствия

1. **Искажение RTT.** Пока `Send` держит лок, reader-горутина не может войти в
   `afterReadLocked` и обработать ACK. Замер RTT берётся после переполучения
   лока — то есть включает время удержания. §3.2 обещает «микросекунды»;
   при большом теле это миллисекунды. Отсюда — завышенный PTO, ложные
   ретрансмиты, деградация congestion control.
2. **Head-of-line blocking между стримами H3.** Весь смысл HTTP/3 —
   независимость стримов. Общий `c.mu` возвращает HOL на уровень процесса:
   пока один стрим заливает тело, никакой другой стрим не может ни отправить,
   ни прочитать.
3. **Reader не может перевзвести read-deadline** — `rearmReadDeadline`
   вызывается из `flushBatch` под тем же локом.

### Дорожная карта F6

| Шаг | Что делаем | Критерий проверки | Оценка |
|---|---|---|---|
| **F6.1** | **Привести реализацию к инварианту §3.2.** `sendLocked` отпускает `c.mu` на границе GSO-батча (каждые ≤64 сегмента): flush, unlock, `runtime.Gosched`-точка, relock, перепроверка состояния стрима/окон (уровень-триггерная перепроверка, как в `acquireSendCredits`). | Новый тест: `Send` большого тела параллельно с приёмом ACK — измеренный ACK-delay < 1 мс; `-race` чист | **M, делать первым** |
| **F6.2** | Бенчмарк конкурентного H3: N горутин × отдельные стримы одного QUIC-соединения, mutex-профиль. Сейчас такого бенча нет — есть только однопоточный `BenchmarkQUICSend` (и тот под env-гейтом). | Бенч в репозитории; базовая линия в BENCH_BASELINE.md | S |
| **F6.3** | Разделить `c.mu` на send-lock и recv-lock там, где состояние действительно разделяется. ## F7. HTTP/3 QPACK — `encMu` сериализует кодирование

### Что происходит

`http3/client.go:781` — `encodeRequestHeaders` берёт `encMu` на время
кодирования заголовков, выкачивания encoder-инструкций и их flush'а.
Все параллельные `Do` на соединении выстраиваются в очередь на CPU-bound
операции.

Смягчения уже есть и они грамотные:
- статический профиль (сервер объявил capacity 0) вообще не берёт лок —
  `qpackEncoder` читается как `atomic.Pointer`;
- декодер **пер-запросный** (`roundTrip`: `var dec qpack.Decoder`), общая
  только динамическая таблица под `qpackMu.RWMutex`;
- блокировка на Required Insert Count (`decodeBlocking` / `waitQPACKInsert`,
  `:881`) сделана правильно — broadcast-каналом с пересозданием, уровень-триггерно,
  ограничена ctx запроса и ctx соединения, лок через ожидание не держится.

Остаётся `encMu` как сериализация на общем динамическом столе — это
неустранимо в рамках RFC 9204 (порядок encoder-инструкций обязан совпадать с
порядком применения на сервере), но размер критической секции сократить можно.
`decWMu` (`:660`) несёт ту же цепочку `flushInstrStream` → `quic.Conn.mu`,
но он лежит на пути reader-горутины и ack'ов, а не на пути `Do`, поэтому
приоритет ниже.

## F8. Rate limiter — глобальный мьютекс и thundering herd

### Что происходит

`client/ratelimit.go:55`, `Take`. Один мьютекс на клиента, берётся на
**каждый** запрос (`client.go:666`, `:917`). При исчерпании токенов:

```go
wait := time.Duration((1 - rl.tokens) / rl.rps * float64(time.Second))
rl.mu.Unlock()
select {
case <-ctx.Done(): ...
case <-time.After(wait):   // аллокация таймера на каждого ждущего, на каждый круг
    rl.mu.Lock()
}
```

Все ждущие вычисляют **одинаковый** `wait`, просыпаются в один момент,
дерутся за один мьютекс, один забирает токен, остальные считают новый
`wait` и ложатся снова. Классический thundering herd с аллокацией таймера
на каждый круг каждого ждущего.

Плюс мёртвый код: `rl.cond` создаётся в `newRateLimiter` (`:35`) и
**нигде не используется** — единственное упоминание во всём пакете.
Doc-комментарий при этом заявляет «sync.Mutex + Cond».

### Дорожная карта F8

| Шаг | Что делаем | Критерий проверки | Оценка |
|---|---|---|---|
| **F8.1** | Удалить `rl.cond` и поправить doc-комментарий (сейчас документация описывает несуществующий механизм). | `grep cond client/ratelimit.go` пуст; комментарий соответствует коду | XS |
| **F8.2** | Быстрый путь без мьютекса: токены как `atomic.Int64` в наноединицах, `CompareAndSwap` на изъятие. Мьютекс остаётся только для пополнения. | Бенчмарк `BenchmarkRateLimiter_Take` при C64: contention → ~0 | M |
| **F8.3** | Убрать herd: одна очередь ожидающих (FIFO), один таймер на лимитер, будящий ровно столько ждущих, сколько токенов накопилось. | Число `time.After` на секунду: O(ждущих) → O(1); честность выдачи в тесте | M |
| **F8.4** | Шардировать лимитер по P с периодической ребалансировкой — для rps > 1e6. Делать только если F8.2/F8.3 не хватило. | Масштабирование по ядрам | L |

## F9. Managed pool / resolver — RWMutex и аллокации на запрос

### Что происходит

tried := make(map[string]struct{})   // аллокация, нужна только при failover

## 11. Что в коде сделано хорошо (и что нельзя сломать)

Чтобы дорожная карта не поехала по уже решённым вещам:

- **`Stream.pushLocked` не блокирует reader.** Любая переделка F2 обязана это
  сохранить: reader-горутина не должна ждать приложение.
- **`Poll` отпускает `c.mu` на время `pc.Read`** и берёт таймстемп RTT после
  переполучения лока. F6.1 должен сохранить обе гарантии.
- **`acquireSendCredits` регистрирует ctx-watcher только при реальной парковке**
  (`context.AfterFunc`), а не на каждый вызов — это уже оптимизировано.
- **Flush перед парковкой в `writeDataVec`** — защита от дедлока, не
  неэффективность. F1.2 убирает flush **только** там, где парковки не будет.
- **Порядок локов в `conn` задокументирован** (`conn/conn.go:86-123`:
  `wmu → psMu → smu → fcOutMu → Stream.mu`). Любое изменение обязано
  обновить этот комментарий, иначе он становится ловушкой.
- **`markStreamDone` держит `smu` на всё тело намеренно** — комментарий прямо
  предупреждает против «сужения для снятия contention». Не трогать.
- **QPACK-блокировка (`decodeBlocking`/`waitQPACKInsert`) сделана правильно**:
  уровень-триггерно, без удержания лока через ожидание, с двойной границей
  по ctx. Это эталон для F3.2.
