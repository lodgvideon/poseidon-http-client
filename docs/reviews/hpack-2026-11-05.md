## Confirmed correctness findings

### P1 — Response fields outlive the decoder callback

[`conn/handler.go:434–470`](https://github.com/lodgvideon/poseidon-http-client/blob/f61188010b90445be8206635573c20d34f482162/conn/handler.go#L434-L470)
retains decoder-owned name/value slices until the whole block is decoded.
The [callback contract](https://github.com/lodgvideon/poseidon-http-client/blob/f61188010b90445be8206635573c20d34f482162/hpack/decoder.go#L46-L49)
permits retaining them only during the callback. Indexed fields alias the
dynamic-table arena; evicting its final entry resets the arena, and a later
literal reuses those bytes before `copyFieldsToBlock` runs.

Reproduction: set both table limits to 64; seed `x-old: a`; then receive
`:status: 200`, indexed `x-old: a`, and incrementally indexed `x-new: b` in
one block. The delivered response contains `x-new: b` twice. Both the name
and value of the earlier field have changed. The
[PUSH_PROMISE callback](https://github.com/lodgvideon/poseidon-http-client/blob/f61188010b90445be8206635573c20d34f482162/conn/handler.go#L613-L618)
uses the same retention pattern.

Copy each field into owned storage while its callback is active, including
the push path. Preserve field ordering and duplicate fields as required by
[RFC 7541 §2.1](https://www.rfc-editor.org/rfc/rfc7541.html#section-2.1).

### P2 — Table-size changes lose their intervening minimum

There are two independent loss points:

- [`conn.go:1646–1647`](https://github.com/lodgvideon/poseidon-http-client/blob/f61188010b90445be8206635573c20d34f482162/conn/conn.go#L1646-L1647)
  collapses repeated `HEADER_TABLE_SIZE` settings to the last value before
  [updating the encoder](https://github.com/lodgvideon/poseidon-http-client/blob/f61188010b90445be8206635573c20d34f482162/conn/conn.go#L1676-L1683).
  After seeding `x-old: a`, one SETTINGS frame containing `0`, then `4096`,
  leaves the old entry available: the next block is `be`, a dynamic index.
- [`encoder.go:92–95`](https://github.com/lodgvideon/poseidon-http-client/blob/f61188010b90445be8206635573c20d34f482162/hpack/encoder.go#L92-L95)
  replaces the pending size with the latest size. Calling
  `SetMaxDynamicTableSize(0)` and then `(4096)` before encoding `:method: GET`
  emits `3f e1 1f 82`; the required minimum update is missing. Expected:
  `20 3f e1 1f 82`.

Apply SETTINGS values in order under the existing write mutex and retain the
smallest pending effective size as well as the final size. Otherwise a peer
cannot perform the same evictions and compression state can diverge.
[RFC 9113 §6.5.3](https://www.rfc-editor.org/rfc/rfc9113.html#section-6.5.3)
defines processing order;
[RFC 7541 §4.2](https://www.rfc-editor.org/rfc/rfc7541.html#section-4.2)
requires signaling the minimum and final sizes, with at most two updates.

### P2 — Decoder accepts a size update after a field

[`decoder.go:251–260`](https://github.com/lodgvideon/poseidon-http-client/blob/f61188010b90445be8206635573c20d34f482162/hpack/decoder.go#L251-L260)
checks the size but not its position in the block. Seed the decoder with
`40 01 78 01 76` (`x: v`), then decode `82 20` (`:method: GET`, size zero).
It returns `nil`; x/net rejects the misplaced update. The streaming sequence
`Begin`, `Feed(82)`, `Feed(20)`, `Finish` also succeeds.

Track whether a field has appeared in the current block, including across
`Feed` calls, and reject later updates. Also cover required updates after a
local limit reduction while introducing that state.
[RFC 7541 §4.2](https://www.rfc-editor.org/rfc/rfc7541.html#section-4.2)
requires size updates at the beginning of a block.

### P2 — DecodeIntegerMax bypasses a small caller ceiling

[`integer.go:43–45`](https://github.com/lodgvideon/poseidon-http-client/blob/f61188010b90445be8206635573c20d34f482162/hpack/integer.go#L43-L45)
returns the prefix value without checking `max`. In the continuation path,
[`max-v`](https://github.com/lodgvideon/poseidon-http-client/blob/f61188010b90445be8206635573c20d34f482162/hpack/integer.go#L58-L63)
underflows when the prefix already exceeds the ceiling.

For prefix width 7 and `max=1`, input `02` returns `(2, 1, nil)`;
`7f 00` returns `(127, 2, nil)`; `7f 7f` returns `(254, 2, nil)`.
Each should return `ErrIntegerOverflow`. Check the initial value before
returning or subtracting it from the ceiling. This affects the public API;
the current internal QPACK caller uses a much larger ceiling and does not
exercise this case. See the implementation-limit requirements in
[RFC 7541 §5.1](https://www.rfc-editor.org/rfc/rfc7541.html#section-5.1).

### P2 — Streaming pending input has no enforced size bound

[`decoder.go:174–179`](https://github.com/lodgvideon/poseidon-http-client/blob/f61188010b90445be8206635573c20d34f482162/hpack/decoder.go#L174-L179)
buffers a truncated field before the header-list limit can be checked.
After `SetMaxHeaderListSize(64)` and `Begin`, feed
`00 01 78 7f 81 ff ff ff 03`: name `x`, declared value length 1 GiB.
Eight further feeds of 1 MiB each all return `nil`. Observed pending length:
8,388,617 bytes; capacity: 9,920,512 bytes, despite the 64-byte list limit.

Reject a literal whose declared length already makes the decoded field
too large, and bound incomplete input. Account separately for Huffman
encoded length and decoded size.
[RFC 7541 §§7.3–7.4](https://www.rfc-editor.org/rfc/rfc7541.html#section-7.3)
discuss memory bounds and implementation limits.

This is a public streaming-API finding. The current HTTP/2 connection uses
`DecodeBlock` and has a separate default 8 MiB compressed-block accumulation
limit in
[`handler.go`](https://github.com/lodgvideon/poseidon-http-client/blob/f61188010b90445be8206635573c20d34f482162/conn/handler.go#L281-L293),
which may be raised by configuration. These checks do not demonstrate
unbounded network memory consumption through that connection path.

## Performance work and ordered follow-ups

The baseline dynamic lookup scans the table. Entry insertion already uses a
FIFO ring; it does not shift every existing entry. It copies incoming bytes
to own them, grows the ring when full, and occasionally
[compacts the arena and entry array](https://github.com/lodgvideon/poseidon-http-client/blob/f61188010b90445be8206635573c20d34f482162/hpack/dynamic_table.go#L164-L189).
That compaction copies live bytes and allocates both arrays. Its cost needs
churn benchmarks, not only repeated-header benchmarks on a warm table.

The first change, `optimize-hpack-dynamic-lookup`, replaces the scan with
encoder-only indexes. Expected constant lookup concerns the number of table
entries; hashing and comparisons still depend on header byte length. All
connection encode calls and encoder resizes already share `wmu`, so this
change needs no additional encoder locks. Decoder lookup remains positional.

Final sequential comparison on Go 1.27.3, Darwin/arm64, Apple M4 Pro:
five samples of 300 ms per case, medians below. The baseline checkout used
the same benchmark file as the changed checkout.

| Case | Baseline | Changed |
|---|---:|---:|
| Oldest match, 8 entries | 26.02 ns | 10.38 ns |
| Oldest match, 64 entries | 191.00 ns | 10.34 ns |
| Oldest match, 512 entries | 1442.00 ns | 10.27 ns |
| Miss, 512 entries | 1434.00 ns | 6.84 ns |
| Oldest value with a repeated name, 512 entries | 1929.00 ns | 22.55 ns |
| Continuous insertion/eviction | 328.8 ns | 122.7 ns |
| Newest match, 512 entries | 4.77 ns | 10.53 ns |
| Warm realistic request | 235.8 ns | 242.1 ns |
| Three static fields | 29.92 ns | 29.05 ns |

Lookup and warm-request cases allocate zero bytes. Churn remains at 72 B/op;
arena compaction still allocates. The newest-entry regression is real, while
the warm-request difference was not statistically resolved in this sample
(`benchstat` p=0.310). Five samples do not provide its 95% confidence interval.
These are codec measurements, not end-to-end HTTP throughput claims.

The index maps are initialized lazily. A cold encoder uses 4768 B / 5
allocations versus the baseline 4720 B / 4 allocations. An encoder that
starts inserting dynamic fields additionally allocates the two maps. Caller
bytes are still copied once into owned storage; the index uses integer
fingerprints without additional string-key copies.

Benchmark command (run separately in each checkout):

```sh
POSEIDON_BENCH_DYNAMIC=1 go test ./hpack -run '^$' \
  -bench '^BenchmarkEncoder_(DynamicLookup|DynamicChurn|DynamicRepeatedName|RealRequest_Warm|EncodeBlock_3req_static)$' \
  -benchmem -count=5 -benchtime=300ms
```

Raw benchmark output and the comparison are stored with the OpenSpec change
in `evidence/`. `BenchmarkEncoder_DynamicConstructor` is separately available
under the same opt-in environment variable.

After that bounded performance change:

1. Fix the P1 callback-lifetime bug in response and push handling, with
   regression tests that force full eviction inside a block.
2. Fix ordered SETTINGS application and minimum/final encoder updates;
   then add decoder block-position and limit-reduction validation.
3. Fix the public integer ceiling and streaming memory-limit cases.
4. Measure and improve arena compaction under sustained insertion/eviction,
   preserving ownership and bounded storage; compare throughput,
   allocations, retained memory, and wire output.
